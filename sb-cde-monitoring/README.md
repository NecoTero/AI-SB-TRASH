# SB_CDE — Мониторинг строительства

Локальный макет 4D/5D-мониторинга. Проект создан с нуля по `PROJECT_SPEC.md`.
Текущий срез реализует импорт XML-графика, версионные снимки, таблицу
операций СМР и начальный read-only просмотр реальной IFC-модели.

## Управление вопросами и известными проблемами

Сводный реестр аудита находится в [manage/README.md](manage/README.md). Там отдельно ведутся нерешённые решения/задачи и временный список ошибок, костылей и противоречий.

## Запуск

Требуется Node.js 22 или новее.

```bash
npm install
npm run dev
```

Откройте <http://localhost:5173>. Frontend работает на `5173`, локальный API —
на `127.0.0.1:3011`. Данные и исходные файлы не отправляются во внешнюю сеть.

Проверки:

```bash
npm test
npm run check
npm run build
```

## Работа через Agent Orchestrator

Репозиторий регистрируется в Orchestrator как самостоятельный Project. Для проекта рекомендуется указать:

- базовую ветку `main`;
- Codex как Worker и Orchestrator;
- `AGENTS.md` как Rules file;
- `npm ci` как Setup command.

В каждом worker создаётся отдельный Git worktree. Команда `npm run dev:ao` и файл `.ao/launch.json` запускают web и API на свободных локальных портах, поэтому параллельные preview не конфликтуют за `5173`/`3011`. Внутри сессии preview открывается командой:

```bash
ao preview start
```

Рабочие импорты `data/schedules` намеренно не входят в Git. Новый worktree получает код и воспроизводимые файлы проекта, но не общие изменяемые снимки другого сеанса.

## Что реализовано

- загрузка XML через браузерную форму;
- при выборе XML отчётная дата автоматически читается из `Project/StatusDate`
  и остаётся редактируемой; исходное значение сохраняется отдельно;
- отчётная дата редактируется в окне «Работы» и автоматически сохраняется в
  текущей версии через 5 секунд после последнего изменения, без создания клона;
- выбранную версию можно удалить из верхней панели; базовая версия защищена от
  удаления, пока к ней привязаны операционные версии;
- первая версия всегда базовая: переключение типа для неё заблокировано;
  следующие версии можно загрузить как базовые или операционные с обязательной
  привязкой к выбранной базе;
- в интерфейсе используются смысловые метки `Базовый`, `Актуальный` и
  `Исторический`; технические номера `Б1`, `О1.1` сохраняются только во
  внутренних метаданных, не перенумеровываются и могут иметь пропуски;
- каждая загрузка создаёт новый неизменяемый снимок;
- в «Мониторинге» всегда открывается актуальная версия; исторические версии
  отображаются неактивными и пока доступны для просмотра только в «Работах»;
- оригинальный XML сохраняется рядом со снимком;
- читается всё поддерево `СМР`, в таблицу попадают строки `Summary=0`, включая
  вехи, если они присутствуют;
- один импорт ограничен 2 500 операциями СМР; превышающий лимит файл не
  сохраняется, пользователь получает сообщение с фактическим количеством;
- родительские строки сохраняются в иерархии, но не показываются операциями;
- все исходные поля операции, вложенные структуры, определения пользовательских
  полей, календари и исходный путь сохраняются без слияния операций;
- `Код КФО` читается только непосредственно из операции и никогда не наследуется;
- операции группируются по КФО, отсутствующий код отображается как `none кфо`;
- группы работ при открытии свёрнуты до первого уровня; на первом уровне
  показано количество входящих операций;
- заголовок группы показывает код КФО вместе с его расшифровкой из поля `КФО`;
- доступны два вида графика: «Работы» с группировкой по активным
  идентификаторам и «Операции» — сворачиваемое дерево, повторяющее исходный
  порядок и уровни поддерева `СМР` из Spider Project;
- дерево поддерживает уровни раскрытия `1…N`, а также команды «Свернуть всё» и
  «Развернуть всё»;
- при первой загрузке выбирается глобальный состав идентификаторов работ:
  КФО обязателен, корпус, секция и этаж включаются независимо;
- активный набор хранится в настройках работ и применяется к многоуровневой
  группировке, агрегации мониторинга и BIM-сопоставлению во всём модуле;
- вкладка «Настройки работ» объединяет отчётную дату выбранной версии и
  двухэкранный мастер идентификаторов: отдельные представления атрибутов и
  вариантов значений; названия IFC-параметров и алиасы сохраняются на сервере;
- технический UID и тип операции сохраняются в данных версии, но не показываются
  пользователю; в таблице выведены плановые и фактические даты;
- единый мастер данных объединяет выбор типа графика, XML и отчётной даты,
  прямой выбор IFC-моделей и настройку идентификаторов; отдельной вкладки импорта
  и самостоятельной кнопки подключения BIM нет;
- исходная и пользовательская отчётные даты хранятся отдельно;
- по умолчанию выбирается последний снимок по эффективной отчётной дате;
- корпус, секция и этаж вычисляются из полного пути операции; существующие
  снимки автоматически дополняются этими полями при первом чтении, исходный XML
  при этом не изменяется;
- для каждой из 1 527 операций рассчитываются отдельно область `Факт / План`,
  статус СМР и отклонение относительно выбранного базового графика;
- IFC-элементы и их количество хранятся на уровне агрегированной «Работы»;
  строкам отдельных операций Express ID и IFC-счётчики не назначаются;
- проценты и объёмы сохраняются, но не участвуют в статусе; противоречивые или
  неполные даты выводятся как диагностика, а не маскируются статусом;
- IFC не подключается автоматически: сначала пользователь выбирает один или
  несколько IFC-файлов из общего списка моделей проекта;
- BIM-шаг единого мастера содержит поиск по IFC-файлам, таблицу выбранных моделей
  и назначение основной IFC, которая меняет геометрию viewer и BIM-связи;
- полная модель читается по поэлементным параметрам
  `REVIT.Код по классификатору / Код по классификатору`,
  `О_*Здание / REVIT.О_*Здание` и
  `О_*Этаж / REVIT.О_*Этаж`; числовой этаж нормализуется в `Этаж N`;
- начальный IFC-вид показывает всю геометрию с прозрачностью 40% (opacity 60%);
- доступны вращение, панорамирование, масштаб, виды и сброс камеры;
- контракт правил маппинга отделён от снимков графика и IFC-геометрии.
- правила из `Статусы и маппинг IFC Временный/README.md` классифицируют 621
  физический IFC-элемент: 551 назначение `rule_based`, 70 — `review`;
- каждый IFC-элемент может быть связан максимум с одной работой; связь создаётся
  только при однозначном совпадении КФО, корпуса, этажа и типа конструкции;
- на контрольном графике однозначно связаны 236 элементов с 6 операциями;
  385 элементов оставлены несвязанными, потому что XML не содержит нужного
  этажа/захватки либо даёт несколько равноправных операций;
- таблица работ показывает статус СМР, отклонение и число связанных элементов;
- кнопка «Привязать модель» открывает выбор модели с реальными локальными
  путями; после подтверждения доступен фильтр «С учетом BIM-данных»;
- в полной модели найдено 6 917 физических элементов; 1 724 имеют КФО, корпус
  и этаж, 1 492 элемента однозначно связаны с 31 работой текущей версии
  графика;
- параметры `REVIT.Код по классификатору` / `Код по классификатору`,
  `REVIT.О_*Здание` / `О_*Здание` / `О_Зона` и варианты параметра этажа
  читаются единым правилом; исходные сочетания КФО и местоположения не
  оцениваются приложением как правильные или ошибочные;
- у 1 407 свай актуального IFC прочитаны корпус из `О_Зона` и этаж
  `Этаж -1`, но в самом файле у них отсутствует значение классификатора,
  поэтому КФО им автоматически не подставляется;
- BIM-фильтр оставляет только работы с однозначно связанными элементами и
  сохраняет родительскую иерархию в режиме дерева;
- экран мониторинга пересчитывает статусы на выбранную дату и окрашивает IFC:
  завершено — зелёным, в работе — болотным, не начато остаётся частью
  полупрозрачного контекста; диагностические случаи показаны янтарным и не
  выдаются за согласованный статус.
- в режиме мониторинга вся модель остаётся видимой как полупрозрачный контекст,
  а завершённые и выполняемые элементы показываются поверх непрозрачными;
- ползунок отменяет устаревшие запросы, Play поддерживает шаги 1, 3 и 7
  календарных дней; снимки графика, разобранные свойства IFC и статическое
  сопоставление кэшируются;
- после первого снимка смена даты передаёт на фронтенд только компактное
  обновление статусов, без повторной отправки BIM-элементов и метаданных работ;
- таймлайн разделён отчётной датой на цветные зоны факта и плана, показывает
  адаптивные недельные и месячные засечки;
- Play ждёт получения и применения снимка текущей даты перед следующим шагом,
  поэтому IFC-модель не пропускает промежуточную перекраску;
- на экране импорта контекстная панель выбранного графика скрыта;
- легенда IFC оформлена крупными цветными карточками для завершённых работ,
  работ в процессе и контекста модели;
- в легенде можно выбрать статусную модель: выполнение работ, проблемы или
  накопительный «Ход строительства»;
  модель проблем окрашивает IFC по отклонению сроков от базового графика
  (просрочка, по графику, опережение, нет расчёта);
- в режиме «Ход строительства» связанный элемент появляется в сам день
  фактического окончания, а при его отсутствии — планового, и далее остаётся
  видимым; будущие, несвязанные и не имеющие окончания элементы скрываются;
- при изменившейся структуре XML межверсионное сопоставление не доверяет
  совпавшим `ID/UID`: используются только однозначные смысловые ключи;
- команда «Фокус на BIM-работах» ограничивает таймлайн датами связанных работ
  с запасом в 7 календарных дней с каждой стороны; повторное нажатие возвращает
  полный диапазон графика;
- для плит, перекрытий и несущего каркаса этой IFC-модели применяется явная
  нормализация к первому этажу; корпус сохраняется из исходного `О_Здание`;

## Локальное хранение

```text
data/schedules/index.json
data/schedules/<scheduleId>/versions/<versionId>/
  source.xml
  snapshot.json
data/mappings/
data/settings/identifiers.json
public/models/RD_KR_04-08.ifc
data/import-preparation/prepared/
  down_PL_CON_13_v2.CMR.operational.xml
  down_PL_CON_13_v2.reconciliation.md
  down_PL_CON_13_v2.issues.csv
Статусы и маппинг IFC Временный/
  README.md
  STATUS_RULES.md
```

`source.xml` сохраняется без изменений. `snapshot.json` содержит полный
разобранный снимок конкретной версии. Новая загрузка не изменяет старые каталоги.

Подготовленный `down_PL_CON_13_v2.CMR.operational.xml` содержит только ветку
СМР и необходимых структурных предков. Он повторно проверен тем же импортёром:
1 743 операции на входе и выходе. Импортировать его следует как операционный
график, выбрав базовую версию по её дате и имени файла; исходный файл v2
остаётся неизменным.

## Проверка реального XML

Фактический результат текущего парсера:

- всего задач `Project/Tasks/Task`: 3 134;
- операций `Summary=0` в полном поддереве СМР: 1 527;
- операций без непосредственного КФО: 1 243;
- `StatusDate`: `2026-07-27T08:00:00`;
- КФО `204.02.02.04`: отдельные UID `1111`, `1273`, `1417`, `1561`;
- вех с `Milestone=1` в выбранном поддереве этого файла: 0.

## Пока не реализовано

- межверсионная идентичность одной и той же операции;
- ручное подтверждение связей `операция → работа → IFC-элемент` и разрешение
  385 неоднозначных/неполных сопоставлений;
- перенос связей на новый снимок графика или новую редакцию IFC;
- подтверждение дополнительных ветвей отклонения для незадержанных
  незавершённых операций, отмеченных в `STATUS_RULES.md` как inference;
- перевод шага таймлайна с календарных дней на рабочие календари XML;
- реальный системный каталог моделей вместо текущей заглушки выбора;
- оболочка по скриншотам SB_CDE: скриншоты ещё не предоставлены.

Неоднозначные элементы не распределяются по работам автоматически. КФО само по
себе не считается достаточным доказательством связи.
