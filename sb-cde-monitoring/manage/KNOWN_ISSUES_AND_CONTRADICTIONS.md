# Временный реестр ошибок, костылей и противоречий

Дата ревизии: 22.10.2026.

Это рабочий «костыльный» файл для накопления проблем до их исправления или переноса в устойчивую документацию. Он не заменяет спецификацию.

## Подтверждённые ошибки и риски реализации

### I-002 · P1 · Общий справочник пока применяется только к IFC

Настройки идентификаторов сохраняются сервером и участвуют в чтении параметров и нормализации значений IFC. `xml-parser.ts` пока использует собственные правила КФО и местоположения, а импорт XLSX не реализован. Пользовательские идентификаторы сверх КФО, корпуса, секции и этажа сохраняются, но ещё не входят в структуру работы.

### I-007 · P1 · Подключение модели — непостоянный клиентский флаг

`modelConnected` хранится только в React state и после перезагрузки снова false. При этом monitoring и модель загружаются независимо. Расчёт есть, но таблица скрывает IFC-счётчики и блокирует фильтр до повторного клика.

### I-012 · P1 · Состав идентификатора «Работы» пока фиксирован в коде

Согласовано целевое правило: КФО обязателен, а корпус, секция, этаж и другие системные идентификаторы пользователь добавляет к ключу «Работы» при импорте через условные «плюсы». Набор хранится на уровне сущности «Работа» для всех версий графика и может редактироваться. Сейчас код фиксированно использует КФО + корпус + этаж, поэтому требуемая настройка ещё не реализована.

### I-015 · P1 · Самописный STEP-парсер IFC хрупок

Он ожидает сущность в одной строке `#id=TYPE(...);`, вручную разбирает аргументы и фиксированные позиции property sets. Другие допустимые варианты IFC могут быть молча пропущены.

### I-016 · P1 · Агрегация может маскировать диагностику

При смеси диагностических и корректных операций `aggregateModelWorkStatus` часто возвращает `in_progress`. Диагностика остаётся текстом, но основной цвет выглядит нормальным.

### I-017 · P1 · Даты проверяются только regex

API и Zod принимают строки вроде `2026-99-99`. Статус сравнивает даты лексикографически, поэтому результат будет правдоподобным, но неверным.

### I-018 · P1 · Все серверные ошибки становятся HTTP 400

Глобальный handler отвечает 400 и на повреждение диска, отсутствие модели, ошибку парсера и внутренний баг. Нельзя отличить клиентскую ошибку, 404, конфликт и 500.

### I-019 · P1 · Warning о StatusDate может быть ложным

Если XML без StatusDate, но пользователь ввёл дату импорта, metadata всё равно пишет «использована текущая локальная дата», хотя применена пользовательская.

### I-020 · P1 · Поиск ветки СМР чувствителен к пробелам

Parser и tree endpoint сравнивают имя с точным `"смр"` без `trim()`. Вспомогательные скрипты trim используют, поэтому инструменты расходятся.

### I-021 · P1 · Snapshot проверяется частично

`readStoredSnapshot` проверяет только верхний уровень и делает type cast, хотя существует полная Zod-схема. Повреждённая операция или дата может попасть в бизнес-логику.

### I-022 · P1 · Не хранится доказательство межверсионной связи

Стратегия matcher вычисляется в памяти и не попадает в snapshot/API/UI. Уникальное название может связать операции при изменившемся КФО; подтвердить или отклонить пару нельзя.

### I-023 · P2 · Два viewer-компонента

Используется `IfcViewerOptimized.tsx`; крупный `IfcViewer.tsx` остаётся альтернативой без ясного статуса.

### I-024 · P2 · Автономный HTML — ручной дубль UI

`sb-cde-prototype.html` вручную дублирует данные и поведение React. Автоматической синхронизации нет.

### I-025 · P2 · Монолитный App.tsx

`src/web/App.tsx` (~65 КБ) содержит API, навигацию, import, monitoring, works, settings, агрегации и диалоги, что затрудняет тестирование и повышает риск регрессий.

### I-026 · P2 · Недостаточное системное тестирование

Unit-тесты не покрывают multipart API, HTTP-коды, repository/перезапуск/удаление, index/snapshot, React-навигацию, viewer и >2 500 операций.

### I-027 · P2 · Артефакты в корне

Есть `*.tsbuildinfo`, `*.stdout.log`, `*.stderr.log`; политика хранения/очистки не описана.

## Противоречия документации и поведения

### D-001 · Импорт отчётной даты

`README.md` утверждает, что выбирается только тип, а дата читается из XML. Текущий UI требует дату и отправляет её как override для базовой и операционной версии.

### D-003 · Группировка операций

`PROJECT_SPEC.md` требует только КФО. UI фиксированно группирует по КФО, названию, корпусу и этажу. README одновременно описывает добавляемые уровни и старую группировку.

### D-004 · «Не начато» во viewer

Спецификация и временные правила требуют скрывать элементы. Viewer показывает полупрозрачный context; README описывает текущее поведение.

### D-005 · Рабочие и календарные дни

Спецификация требует рабочие дни по календарям XML. Реализация и README используют календарные 1/3/7 дней. Календари только сохраняются.

### D-006 · Число элементов полной IFC-модели

Основной README утверждает 6 917 элементов. Фактический cache schema v6 и `data/mappings/README.md` содержат 5 491. Все 5 491 сейчас имеют КФО, корпус и этаж.

### D-007 · Однозначность и тип конструкции

Основной README говорит о совпадении КФО, корпуса, этажа и типа конструкции. Актуальный mapping README и код v2 используют КФО + корпус + этаж, не используют IFC-класс/тип и допускают несколько операций внутри работы.

### D-008 · Выбор моделей

`PROJECT_SPEC.md` говорит об одной модели и заглушке. Сейчас две жёстко заданные модели, реальный viewer и radio-выбор одной активной модели; UI использует множественное число.

### D-009 · Сохранение исходного XML

В спецификации сохранение XML обозначено как несогласованное. Реализация и README считают `source.xml` постоянной частью хранилища.

### D-011 · Статус требований

`PROJECT_SPEC.md` говорит, что формулы статусов будут определены позднее. `Статусы и маппинг IFC Временный/STATUS_RULES.md` и код уже содержат формулы, но документ остаётся «временным».

### D-012 · Контрольные числа README

Числа 236/385/1 492/31 и 6 917 не проверяются обычным test/build, зависят от конкретной версии данных и частично уже не совпадают с текущим кэшем.

## Подтверждённо корректно на текущем срезе

- Два snapshot соответствуют index по метаданным и числу операций.
- Исходный XML хранится рядом со snapshot.
- КФО операции не наследуется от родителя.
- Основные статусные границы покрыты unit-тестами.
- Geometry cache валидируется по size/mtime; проблема постоянного in-memory cache относится к IFC-маппингу, не к geometry cache.

## Решённые пункты — DONE

### I-001 · DONE · Скрипт подготовки операционного XML не запускался

Неиспользуемый `scripts/prepare-operational-export.ts` удалён вместе с устаревшими ссылками. Подготовленные XML и отчёты сохранены как данные проекта.

### I-003 · DONE · «Сохранить график» создавало версию без новых данных

Кнопка и endpoint `save-operational` удалены. Изменение отчётной даты в «Работах» через 5 секунд обновляет метаданные текущей версии и соответствующий snapshot, не копируя XML и операции.

### I-006 · DONE · В «Мониторинге» можно было перейти на неактуальную версию

При входе в «Мониторинг» выбираются наиболее недавно обновлённый график и его актуальная версия. Исторические версии показаны неактивными; попытка выбора выводит уведомление. Выбор исторических версий остаётся доступен в «Работах».

### I-004 · DONE · IFC-элементы ошибочно назначались каждой операции

Express ID и количество IFC-элементов удалены из фактической связи на уровне операции. Они хранятся и отображаются только у агрегированной сущности «Работа». Отдельная связь IFC-элемента с операцией в текущем макете не предусматривается.

### I-005 · DONE · Таблица могла молча обрезать график после 2 500 операций

Лимит 2 500 зафиксирован как продуктовое ограничение. Импорт с большим количеством операций останавливается до записи данных и возвращает пользователю сообщение с фактическим количеством и лимитом. Для старых данных frontend также проверяет `total` и предупреждает об обрезании.

### I-008 · DONE / принято для макета · Множественная терминология при одной активной модели

Для реального MVP планируется работа с несколькими IFC. В текущем макете одна модель активна одновременно, а множественное число в текстах сознательно сохраняется как отражение целевого процесса.

### I-014 · DONE / принято для макета · Legacy IFC-маппинг зашит под первую модель

Жёсткие fallback-КФО, семейства и принудительный первый этаж признаны временным костылём только для первой модели макета. В MVP эти правила не должны заменять настраиваемый маппинг.

### I-009 · DONE · Метки версий больше не перенумеровываются

Пользователь видит смысловые метки `Базовый`, `Актуальный` и `Исторический`.
Технические `Б1`, `О1.1` оставлены только во внутренних метаданных, после
удаления не меняются и повторно не используются; пропуски допустимы.

### I-010 · DONE / принято для однопользовательского макета · Нет блокировки параллельной записи

Одновременные import/delete не входят в сценарий эксплуатации макета. Риск
потерянного обновления сознательно принят; перед многопользовательским MVP
понадобится транзакционное хранилище, lock или CAS.

### I-011 · DONE / принято для макета · Инвалидация кэшей

Кэши monitoring очищаются после удаления версии графика, а кэши IFC и
monitoring — после сохранения настроек идентификаторов. Замена IFC-файла по тому
же пути во время работы сервера не является пользовательским сценарием макета;
после такой ручной замены требуется перезапуск.

### I-013 · DONE · Отсутствующий этаж больше не означает «любой этаж»

Работа модели сопоставляется только при полном совпадении КФО, корпуса и этажа.
При отсутствии идентификатора или подходящей работы графика она показывается со
стороны «Модель» с предупреждением `Нет данных`, а её элементы не участвуют в
расчётном статусе.

### D-010 · DONE · Пользовательские и технические метки версий разделены

Интерфейс использует `Базовый`, `Актуальный` и `Исторический`. Внутренние номера
неизменяемы, а редактируемая отчётная дата синхронно записывается в index и
snapshot без создания нового снимка.

### D-002 · DONE · README называл настройки идентификаторов заглушкой

README и интерфейс актуализированы: настройки сохраняются сервером и применяются к IFC; граница по XML/XLSX указана явно.
