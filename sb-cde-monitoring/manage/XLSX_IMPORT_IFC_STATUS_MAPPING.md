# Импорт единой XLSX-формы, статусы работ и маппинг с IFC

Статус документа: аналитическая постановка для проектирования и разработки.  
Дата анализа: 22.10.2026.

Документ описывает, как встроить в «Мониторинг» регулярно поступающую XLSX-форму прогресса, не потерять исходные данные и связать строки графика с работами IFC. Подтверждённые правила отделены от решений, которые ещё нужно согласовать.

## 1. Коротко о предлагаемой схеме

1. Каждый XLSX-файл импортируется как отдельный неизменяемый снимок на отчётную дату.
2. Отчётная дата читается из ячейки `R3` листа `График`. Имя файла используется только как подпись и проверка.
3. Строка Excel становится операцией. КФО не является идентификатором операции и не объединяет строки.
4. `Код операции Графика` из столбца `A` используется как кандидат на межверсионный ключ. Его уникальность и отсутствие переиспользования проверяются при каждом импорте.
5. Исходными считаются значения `A:T`. Расчётные столбцы `U:AI` сохраняются для аудита, но канонические показатели система пересчитывает сама.
6. Операции связываются с IFC не напрямую. Сначала из операций строятся работы графика, из элементов IFC — работы модели, затем сопоставляются работы.
7. Текущая реализация связывает работы по точному ключу `КФО + корпус + этаж`.
8. XLSX почти не содержит дат фактического начала и окончания. Поэтому существующую статусную модель по датам нельзя применять к форме без дополнительного бизнес-решения. До решения система должна показывать диагностику, а не выдумывать статус и цвет IFC.

## 2. Что обнаружено в двух файлах

Проверены:

- `Прогресс_40КН_Отель The Wave_2026.10.04.xlsx`;
- `Прогресс_42КН_Отель The Wave_2026.10.11.xlsx`.

Оба файла содержат один рабочий лист `График`. Заголовок таблицы находится в строке 7, данные начинаются со строки 8.

| Проверка | 40 КН | 42 КН |
| --- | ---: | ---: |
| Отчётная дата в `R3` | 04.10.2026 | 18.10.2026 |
| Строк данных | 2 444 | 2 444 |
| Строк `СМР` | 2 443 | 2 443 |
| Строк `ПНР` | 1 | 1 |
| Уникальных кодов операции `A` | 2 444 | 2 444 |
| Дубли кодов операции `A` | 0 | 0 |
| Уникальных КФО | 86 | 86 |
| Уникальных дисциплин | 39 | 39 |
| Пустых кодов КФО | 0 | 0 |
| Пустых наименований КФО | 2 | 2 |

Существенные наблюдения:

- В имени второго файла указано `2026.10.11`, но внутренняя отчётная дата `R3` равна `18.10.2026`. Система не должна определять отчётную дату по имени файла.
- Набор кодов операций в двух файлах полностью совпадает. В пределах этих двух снимков столбец `A` выглядит стабильным.
- Названия в столбце `B` изменились у 2 368 из 2 444 операций. Во второй версии к названиям в основном добавлены корпус, секция, этаж или зона. Название нельзя использовать как основной межверсионный ключ.
- Плановые даты `M:N`, общие объёмы `Q:R` и накопленный факт `T` между файлами не изменились. Плановый накопительный объём `S` изменился только у двух операций.
- `Начало Актуальное` в `O` заполнено у одной операции. `Окончание Актуальное` в `P` не заполнено ни у одной операции.
- Фактический прогресс больше нуля есть только у одной операции. В ней `T / R = 50,52%`.
- В строке 2403 столбец `N` содержит текст `ё` вместо даты. Это подтверждает необходимость построчной диагностики, а не молчаливого преобразования ошибки в пустое значение или ноль.
- Во втором файле заголовок `Z` повторяет `Факт ФО`, хотя формула столбца остаётся `Z = T × G`. По смыслу это фактические трудозатраты. Импорт нельзя строить только на тексте этого динамического заголовка.
- Поля после `T` в основном являются формулами Excel. Внешних ссылок в проверенном файле нет. Значения формул сохранены в кэше книги, но этот кэш может оказаться устаревшим в другом файле.
- Фактические данные находятся только до столбца `AI`. Диапазон до `KI` во втором файле образован форматированием, а не значениями.

Эти числа являются контрольными только для двух проверенных файлов. Они не должны становиться жёсткими ограничениями импортера.

## 3. Контракт входного файла

### 3.1. Метаданные

| Ячейка | Значение | Правило импорта |
| --- | --- | --- |
| `R1` | Год | Контрольное поле. Не заменяет отчётную дату. |
| `R2` | Номер КН | Метка отчётного периода. Сохранять как исходное значение. |
| `R3` | Отчётная дата | Основной источник `report_date`. Хранить как календарную дату без часового пояса. |

Проверки:

- `R3` должна быть корректной Excel-датой;
- год в `R1` должен совпадать с годом `R3`, иначе предупреждение;
- номер КН в `R2` и дата в имени файла могут не совпасть с вычисленным номером недели; это предупреждение, а не автоматическое исправление;
- при отсутствии `R3` импорт не должен сам брать дату из имени файла. Нужен явный ввод пользователя.

### 3.2. Поля операции

| Столбец | Исходное поле | Нормализованное поле системы | Комментарий |
| --- | --- | --- | --- |
| `A` | Код операции Графика | `source_operation_code` | Кандидат на стабильный ключ между версиями. Хранить как строку. |
| `B` | Название операции Графика | `name` | Может меняться между версиями. Используется также как источник признаков местоположения. |
| `C` | Этап | `stage` | `СМР` участвует в текущем 4D-мониторинге. `ПНР` хранится, но не смешивается с СМР. |
| `D` | Дисциплина | `discipline` | Справочный атрибут и возможный дополнительный идентификатор работы. |
| `E` | Код КФО | `kfo_code` | Обязательная часть идентификатора работы, но не идентификатор операции. |
| `F` | Наименование КФО | `kfo_name` | Может отсутствовать. Код не обнулять. |
| `G` | Удельные трудозатраты | `labor_hours_per_unit` | Часы на единицу физического объёма. |
| `H` | Подрядчик | `contractor` | В проверенных файлах заполнен только у 23 строк. |
| `I:J` | Объект: код и название | `object_code`, `object_name` | Сохранять раздельно. |
| `K:L` | Подобъект: код и название | `subobject_code`, `subobject_name` | Сохранять раздельно. |
| `M` | Начало ЦП | `baseline_start` | Дата контрольного плана. |
| `N` | Окончание ЦП | `baseline_finish` | Дата контрольного плана. Невалидное значение не превращать в `null` без диагностики. |
| `O` | Начало Актуальное | Требует решения | Нельзя автоматически считать фактическим началом. См. раздел 6. |
| `P` | Окончание Актуальное | Требует решения | Нельзя автоматически считать фактическим окончанием. См. раздел 6. |
| `Q` | Всего по проекту, ЦП | `baseline_total_quantity` | Физический объём контрольного плана. Единица измерения в форме отсутствует. |
| `R` | Всего по проекту, актуальное | `current_total_quantity` | Текущий общий физический объём. |
| `S` | План накопительный на КН | `planned_quantity_at_report_date` | Плановая накопленная физическая величина на `R3`. |
| `T` | Факт ФО на КН | `actual_quantity_at_report_date` | Накопленный факт на `R3`. Снимки не суммировать. |

### 3.3. Расчётные поля Excel

Система должна пересчитывать эти показатели из исходных значений. Кэшированное значение и формулу Excel следует сохранять в `raw` для аудита.

| Столбец | Формула в проверенных файлах | Канонический смысл |
| --- | --- | --- |
| `U` | `T - S` | Отклонение фактического объёма от накопительного плана |
| `V` | `R - T` | Остаток физического объёма |
| `W` | `G × Q` | Трудозатраты по контрольному плану |
| `X` | `G × R` | Актуальные общие трудозатраты |
| `Y` | `G × S` | Плановые накопительные трудозатраты |
| `Z` | `G × T` | Фактические накопительные трудозатраты |
| `AA` | `G × U` | Отклонение трудозатрат |
| `AB` | `G × V` | Остаток трудозатрат |
| `AC` | `S / Q` | Доля планового выполнения операции по контрольному объёму |
| `AD:AE` | Взвешенный плановый прогресс | Доля операции в общем плане проекта |
| `AF` | `IF(T>R,1,T/R)` | Фактическая доля выполнения, ограниченная сверху единицей |
| `AG:AH` | Взвешенный фактический прогресс | Доля операции в общем факте проекта |
| `AI` | `AG - AD` | Отклонение взвешенного фактического прогресса от планового |

Особенности, которые импортёр не должен скрывать:

- `AF` в книге возвращает `0` при ошибке деления и ограничивает результат единицей при `T > R`. Так теряются различия между отсутствием знаменателя, реальным нулём и перевыполнением.
- Канонический `actual_progress_ratio` должен быть `null`, если `R` отсутствует или не больше нуля. Для `T > R` нужно хранить реальное отношение и отдельный признак `actual_quantity_exceeds_total`.
- Единица физического объёма отсутствует. Физические объёмы разных операций нельзя суммировать как однородную величину. Трудозатраты можно агрегировать только после проверки `G`.
- `U` и `AI` — отклонения по объёму и прогрессу. Они не заменяют отклонение по срокам `Просрочена / По графику / Опережение`.

## 4. Алгоритм импорта

### 4.1. Проверка структуры

Импортёр должен искать договорной набор заголовков, а не просто читать диапазон `A7:AI...` вслепую.

1. Найти лист `График`.
2. Найти строку заголовка по обязательным полям `Код операции Графика`, `Название операции Графика`, `Этап`, `Код КФО`, `Начало ЦП`, `Окончание ЦП`.
3. Проверить наличие всех столбцов `A:T`.
4. Для динамических заголовков `S`, `T`, `Y`, `Z` проверить общий смысл и позицию. Номер КН в тексте заголовка не является частью имени поля системы.
5. Не считать форматирование после `AI` данными.
6. Сохранить версию контракта импортера, исходное имя файла, размер, SHA-256 и время импорта.

Изменение порядка или состава обязательных столбцов должно завершаться ошибкой схемы с перечнем отличий. Незначительное изменение текста динамического заголовка допускается только при совпадении позиции и остальных контрольных признаков.

### 4.2. Чтение строк

1. Читать строки после заголовка до последнего непустого `A`.
2. Сохранять номер строки Excel как `source_row_number`, но не использовать его как бизнес-ключ.
3. Строковые идентификаторы не преобразовывать в числа.
4. Даты читать с учётом системы дат конкретной книги Excel. В систему записывать `YYYY-MM-DD`, исходное числовое значение сохранять в `raw`.
5. Числа читать как числа, пустую ячейку сохранять как отсутствие значения. Пустое значение не равно нулю.
6. Строки `СМР` и `ПНР` сохранять. В текущую выборку 4D включать только `СМР`.
7. Каждую ошибку привязывать к файлу, листу, строке, столбцу, исходному значению и коду операции.

### 4.3. Минимальные проверки строки

- `A`, `B`, `C`, `E`, `M`, `N` должны быть заполнены для обычной операции СМР;
- `A` должен быть уникален внутри снимка;
- `M` и `N` должны быть датами, `M ≤ N`;
- `G`, `Q`, `R`, `S`, `T` должны быть числами не меньше нуля;
- `S ≤ Q` и `T ≤ R` проверяются как бизнес-диагностика, но превышение не должно автоматически обрезаться;
- `F` может отсутствовать при наличии `E`, но это предупреждение о неполном справочнике;
- неизвестный этап не заменяется на `СМР`;
- ошибочная дата, например `N = "ё"`, блокирует расчёты зависимой операции, но не требует отклонять весь файл, если выбран режим частичного импорта с диагностикой.

Рекомендуется сохранять снимок только после формирования полного отчёта проверки. Режимы `отклонить весь файл` и `сохранить корректные строки с диагностикой` должны быть явной настройкой процесса, а не скрытым поведением.

### 4.4. Версионность

- Каждая загрузка создаёт новую версию. Предыдущая версия не перезаписывается.
- `R3` становится `source_status_date` и по умолчанию `effective_status_date`.
- Значения `T` и производные проценты являются накопленной точкой именно на дату версии. Значения разных версий не складываются.
- Актуальная версия определяется максимальной `effective_status_date`, при равенстве — временем импорта.
- Отсутствующая в новом снимке операция не удаляется из истории. Для неё создаётся признак `removed_from_current_snapshot`.
- Новая операция получает признак `new_in_current_snapshot` и не считается автоматически завершённой или просроченной.

## 5. Идентичность операции между версиями

Для двух проверенных файлов рекомендуется следующий порядок:

1. Точное уникальное совпадение `source_operation_code` из `A`.
2. Проверка защитных признаков: КФО, этап, дисциплина, объект и подобъект.
3. При изменении защитных признаков — статус `identity_review`, а не автоматическое соединение.
4. Если код пропал, появился второй раз или был переиспользован для другой работы — ручное сопоставление или создание новой логической операции.

Название не входит в основной ключ: оно изменилось у 96,9% строк между проверенными снимками. КФО также не является ключом: один КФО соответствует множеству операций.

В данных нужны два идентификатора:

- `snapshot_operation_id` — уникальная строка конкретной версии;
- `logical_operation_id` — одна операция во времени, полученная после межверсионного сопоставления.

Для каждой связи следует хранить стратегию, уровень доверия, использованные признаки и признак ручного подтверждения.

## 6. Статусы операций

### 6.1. Текущая согласованная модель системы

Существующая система рассчитывает три независимых признака:

| Признак | Значения |
| --- | --- |
| Область выбранной даты | Факт / План |
| Статус СМР | Не начато / В работе / Завершено / Требует данных |
| Отклонение по срокам | Просрочена / По графику / Опережение / Нет базы / Нет данных |

Обозначения:

- `T` — выбранная пользователем дата таймлайна;
- `R` — отчётная дата версии;
- `A` — текущий операционный снимок;
- `B` — связанный базовый снимок;
- `ФН`, `ФО` — фактическое начало и окончание;
- `АН`, `АО` — актуальное плановое начало и окончание;
- `БН`, `БО` — базовое начало и окончание.

В этом подразделе `T` означает выбранную дату таймлайна. Это не столбец `T` Excel с фактическим физическим объёмом.

Область даты:

- `T ≤ R` — факт;
- `T > R` — план.

Фактическая область:

1. `ФО ≤ T` — `Завершено`.
2. `ФН ≤ T` и завершение ещё не наступило — `В работе`.
3. Фактическое начало не наступило — `Не начато`.
4. Противоречивые или необходимые отсутствующие даты — `Требует данных` с диагностикой.

Плановая область:

1. Известный завершённый факт имеет приоритет.
2. Если `АО < R`, а `ФО` нет, операция остаётся `В работе` и получает просрочку. Она не завершается автоматически.
3. Если `АО > R` и `T ≥ АО`, допускается плановое `Завершено`, не создающее фактического окончания и фактического объёма.
4. Фактически начатая операция не возвращается в `Не начато`.
5. Случай `АО = R` без `ФО` пока остаётся диагностическим до отдельного решения.

Отклонение по срокам:

- до завершения проверяются задержка старта и пропуск базового окончания;
- после завершения фактическое или плановое окончание сравнивается с `БО`;
- равенство общих статусов A и B само по себе не означает `По графику`;
- отсутствие базовой операции означает `Нет базы`, а не `По графику`.

### 6.2. Почему этой модели недостаточно для проверенной XLSX-формы

В форме есть базовые даты `M:N`, накопительный план `S` и накопленный факт `T`, но почти нет значений `O:P`. Кроме того, название `Актуальное` не доказывает, что `O:P` являются фактическими датами.

Следовательно, без дополнительного решения нельзя:

- присвоить `Не начато` только потому, что `T = 0`;
- присвоить `В работе` только потому, что `0 < T < R`;
- присвоить `Завершено` только потому, что `T ≥ R`;
- восстановить дату начала или окончания из недельного накопленного факта;
- вычислить статус на произвольную дату между двумя отчётными снимками;
- использовать `U` или `AI` как отклонение по срокам.

Такое ограничение соответствует действующим правилам проекта: проценты и объёмы сохраняются, но пока не определяют статус СМР.

### 6.3. Что можно рассчитывать без нового бизнес-правила

Для каждой операции и каждой версии можно безопасно рассчитать отдельный признак `progress_evidence`:

| Условие на отчётную дату | Значение `progress_evidence` |
| --- | --- |
| `R` или `T` отсутствует, `R ≤ 0`, значение нечисловое | `invalid_or_missing` |
| `T = 0`, `R > 0` | `zero_reported` |
| `0 < T < R` | `partial_reported` |
| `T = R`, `R > 0` | `full_reported` |
| `T > R`, `R > 0` | `overrun_reported` |

Это доказательство из источника, а не статус СМР. Оно не должно окрашивать IFC до утверждения правила перехода.

Если фактические даты не определены, результат статусного расчёта должен быть:

- `construction_status = diagnostic`;
- `diagnostic_code = XLSX_STATUS_SOURCE_NOT_CONFIRMED`;
- пояснение с указанием отсутствующего или неутверждённого источника.

### 6.4. Вариант для согласования: статус из физического факта

Ниже приведён реализуемый вариант, но он не является действующим правилом проекта.

На самой отчётной дате версии:

| Условие | Предлагаемый статус |
| --- | --- |
| `T = 0`, `R > 0` | Не начато |
| `0 < T < R` | В работе |
| `T ≥ R`, `R > 0` | Завершено |
| Данные отсутствуют или противоречивы | Требует данных |

Чтобы принять этот вариант, нужно отдельно подтвердить:

1. что `T` является надёжным накопленным физическим фактом по каждой операции;
2. что нулевой факт однозначно означает отсутствие начала;
3. что достижение общего актуального объёма означает завершение операции;
4. как учитывать переоценку общего объёма `R` между версиями;
5. как показывать дни между отчётными датами: только точки, последнее известное значение или иной алгоритм;
6. как прогнозировать статус справа от отчётной даты.

До подтверждения система может показывать процент и доказательство прогресса рядом со статусом, но не подменять ими согласованный статус.

## 7. Базовый и операционный графики внутри одной формы

Форма одновременно содержит показатели контрольного плана и актуального состояния. Это отличается от текущей модели, где базовый и операционный графики загружаются отдельными снимками.

Предлагаемое представление:

- одна загрузка XLSX создаёт операционную версию на дату `R3`;
- `M`, `N`, `Q` образуют встроенный срез контрольного плана;
- `O`, `P`, `R`, `S`, `T` образуют актуальный срез, после уточнения смысла `O:P`;
- при первой загрузке контрольный срез может стать базовой редакцией;
- при следующих загрузках `M`, `N`, `Q` сравниваются с выбранной базовой редакцией;
- изменение контрольного среза не перезаписывает базу молча. Требуется новая редакция базы или явное подтверждение привязки.

Для каждой операции следует хранить одновременно базовые, актуальные и фактические поля, а не перетирать одни другими.

## 8. Формирование работ графика

Работа графика — агрегирующая сущность. Операции внутри неё остаются отдельными строками и получают отдельные статусы.

Рекомендуемый минимальный системный ключ работы:

`КФО + корпус + этаж`

Он совпадает с текущей реализацией для IFC-модели v2. Секция может стать дополнительным идентификатором после появления надёжного значения на обеих сторонах.

Из XLSX признаки местоположения могут быть извлечены только из явно распознанных фрагментов названия `B`, например:

- `Корпус A`;
- `Секция C4`;
- `1 этаж`;
- `тех. этаж`;
- `кровля`.

Для каждого извлечённого значения нужно хранить:

- исходный фрагмент;
- нормализованное значение;
- правило и версию правила;
- уровень доверия;
- признак ручного подтверждения.

Запрещено автоматически считать, что буква секции равна корпусу IFC, а `тех. этаж` равен `Этаж -1`, пока не утверждена таблица соответствий.

## 9. Маппинг работ графика с IFC

### 9.1. Текущая модель IFC

В актуальном кэше модели v2 находится 5 491 элемент:

| Признак | Значения |
| --- | --- |
| Корпуса | `Корпус А`, `Корпус Б`, `Корпус В` |
| Этажи | `Этаж -1`, `Этаж 1` ... `Этаж 7` |
| Секции | не заполнены |
| КФО | `204.02.02.02`, `204.02.02.05`, `204.02.03.01`, `204.02.03.02` |

В XLSX есть операции только для трёх из четырёх КФО модели:

| КФО | Операций XLSX | Элементов IFC | Предварительный вывод |
| --- | ---: | ---: | --- |
| `204.02.02.02` | 0 | 1 407 | Автоматическая связь невозможна: КФО отсутствует в графике. |
| `204.02.02.05` | 67 | 1 434 | Есть КФО, но в названиях указаны секции, а не явные корпуса; этаж требует нормализации. |
| `204.02.03.01` | 83 | 1 223 | Есть КФО; у части строк есть этаж, у большинства местоположение задано через секцию. |
| `204.02.03.02` | 63 | 1 427 | Есть КФО; у части строк есть этаж, у большинства местоположение задано через секцию. |

Совпадение КФО само по себе недостаточно: оно связало бы одну операцию сразу с элементами нескольких корпусов и этажей.

### 9.2. Последовательность маппинга

1. Прочитать исходные идентификаторы операции и элемента IFC.
2. Нормализовать значения по версионным справочникам алиасов.
3. Сформировать работу графика по выбранному полному ключу.
4. Сформировать работу модели по тому же набору системных идентификаторов.
5. Автоматически связать только одно полное и однозначное совпадение ключа.
6. Все частичные, множественные и конфликтующие совпадения отправить на проверку.
7. Сохранить связь, версию правил, исходные значения и объяснение результата.
8. После изменения правил пересчитать связи, не изменяя исходные операции и IFC-элементы.

Кардинальности:

- одна работа графика содержит много операций;
- одна работа модели содержит много IFC-элементов;
- одна связанная работа объединяет одну работу графика и одну работу модели;
- один IFC-элемент относится только к одной работе и не получает несколько конфликтующих цветов.

### 9.3. Необходимый справочник нормализации

Для этой формы нужен отдельный управляемый справочник как минимум со следующими полями:

| Поле | Назначение |
| --- | --- |
| `source_section` | Значение из названия операции, например `Секция C4` |
| `system_building` | Подтверждённый корпус IFC |
| `system_section` | Нормализованная секция, если она нужна в ключе |
| `source_floor_token` | `1 этаж`, `тех. этаж`, `кровля` и другие варианты |
| `system_floor` | Подтверждённый этаж IFC |
| `kfo_scope` | Ограничение правила конкретными КФО при необходимости |
| `rule_revision` | Версия правила |
| `status` | Черновик / подтверждено / выведено из действия |
| `evidence` | Основание и автор подтверждения |

Неподтверждённое правило не должно создавать производственную связь.

## 10. Агрегация статусов на работу и IFC

Текущая реализация агрегирует статусы операций одной работы так:

- все операции завершены — работа `Завершена`;
- все операции не начаты — работа `Не начата`;
- любое смешанное состояние — работа `В работе`;
- если нет пригодных статусов — `Требует данных`;
- отклонение выбирается по приоритету: `Просрочена` → `Нет данных` → `Нет базы` → `Не рассчитано` → `По графику` → `Опережение`.

Эта агрегация реализована, но её следует отдельно утвердить как бизнес-правило. В частности, наличие диагностической операции вместе с корректными операциями сейчас может привести к агрегированному `В работе`. Для безопасного режима рекомендуется отдельный признак `status_quality = partial_data`, чтобы работа не выглядела полностью рассчитанной.

После утверждения статуса работы он распространяется на все элементы связанной работы модели:

| Статус работы | Отображение IFC |
| --- | --- |
| Не начато | скрыто в режиме выполнения |
| В работе | зеленовато-синий/болотный цвет |
| Завершено | зелёный цвет |
| Требует данных | отдельный диагностический вид, без выдачи цвета за рассчитанный статус |

Начальный полупрозрачный обзор всей модели является отдельным режимом и не означает статус операции.

## 11. Рекомендуемые сущности хранения

### `schedule_version`

- идентификатор версии;
- тип и базовая редакция;
- исходное имя, SHA-256 и размер файла;
- дата импорта;
- `source_status_date`, `effective_status_date`;
- номер КН;
- версия контракта XLSX;
- итог проверки и список предупреждений.

### `operation_snapshot`

- `snapshot_operation_id`;
- `logical_operation_id`;
- `source_operation_code`, `source_row_number`;
- поля `A:T` в нормализованном виде;
- исходные значения всех ячеек;
- формулы и кэшированные значения `U:AI`;
- извлечённое местоположение и происхождение каждого признака;
- диагностические коды.

### `operation_measurement`

- версия и отчётная дата;
- логическая операция;
- плановый накопительный объём `S`;
- фактический накопительный объём `T`;
- общий актуальный объём `R`;
- вычисленное отношение без обрезки;
- единица измерения или `unknown`;
- качество данных.

### `schedule_work` и `model_work`

- состав и значения системного ключа;
- перечень операций или IFC-элементов;
- версия правил нормализации;
- качество идентификаторов.

### `work_mapping`

- работа графика и работа модели;
- автоматический или ручной способ;
- версия правил;
- статус подтверждения;
- объяснение совпадения;
- дата создания и автор решения.

Расчётный статус не записывается обратно в исходный снимок. Он хранится или кэшируется с обязательной ссылкой на версию графика, базовую версию, выбранную дату и версию статусных правил.

## 12. Диагностические коды

Минимальный набор:

| Код | Смысл |
| --- | --- |
| `XLSX_SCHEMA_MISMATCH` | Не совпал обязательный состав формы |
| `REPORT_DATE_MISSING` | Нет корректной отчётной даты |
| `REPORT_DATE_FILENAME_MISMATCH` | Дата внутри файла не совпадает с именем |
| `DUPLICATE_OPERATION_CODE` | Код операции повторяется в снимке |
| `OPERATION_IDENTITY_CONFLICT` | Код переиспользован для другой работы |
| `INVALID_DATE` | Некорректная дата операции |
| `INVALID_NUMBER` | Некорректное числовое значение |
| `MISSING_KFO_NAME` | Есть код КФО, но нет названия |
| `QUANTITY_UNIT_UNKNOWN` | В форме нет единицы физического объёма |
| `ACTUAL_EXCEEDS_CURRENT_TOTAL` | Накопленный факт больше актуального общего объёма |
| `FORMULA_CACHE_MISMATCH` | Кэш Excel не совпал с серверным пересчётом |
| `XLSX_STATUS_SOURCE_NOT_CONFIRMED` | Нельзя рассчитать статус по действующим правилам |
| `LOCATION_NOT_RESOLVED` | Не определён корпус, секция или этаж |
| `IFC_WORK_NOT_FOUND` | Для работы графика нет полного совпадения в IFC |
| `IFC_WORK_AMBIGUOUS` | Найдено несколько кандидатов |
| `BASELINE_OPERATION_NOT_FOUND` | Нет соответствующей операции в базе |

## 13. Решения, необходимые до производственной реализации статусов и раскраски

1. Что именно означают `Начало Актуальное` и `Окончание Актуальное`: текущие плановые даты или фактические даты события?
2. Разрешено ли определять статус СМР по `T / R`, когда фактические даты отсутствуют?
3. Как показывать статус между отчётными датами: только в точках снимков, последнее известное значение или другой алгоритм?
4. Какая таблица связывает секции из названия операции с корпусами IFC?
5. Как нормализовать `тех. этаж`, `кровля`, отсутствие этажа и другие зоны?
6. Должна ли секция входить в ключ работы, если в текущей IFC она не заполнена?
7. Как трактовать изменение `M`, `N`, `Q` между файлами: новая редакция базы или изменение операционного графика?
8. Является ли `A` гарантированно стабильным идентификатором во всех будущих выгрузках?
9. Как агрегировать диагностические операции на работу: блокировать цвет целиком или показывать частичное качество?
10. Какой источник истины использовать при расхождении серверного пересчёта с кэшем формул Excel?

До ответов можно реализовать импорт, версионность, хранение измерений, отчёт качества и подготовку работ. Автоматическую окраску IFC по неподтверждённому статусу включать нельзя.

## 14. Приёмочные проверки

### Импорт

- оба контрольных файла читаются как отдельные версии;
- из `R3` получаются даты `04.10.2026` и `18.10.2026`;
- считываются 2 444 строки, из них 2 443 СМР и 1 ПНР;
- 2 444 кода операций уникальны;
- ошибка `N2403 = "ё"` попадает в диагностику и не превращается в дату или ноль;
- дата из имени второго файла не заменяет внутреннюю дату;
- пустое значение отличается от нуля;
- значения после `AI` не принимаются за данные;
- формулы пересчитываются сервером, расхождения с кэшем фиксируются.

### Версии и идентичность

- новая загрузка не изменяет старый снимок;
- одинаковые коды `A` связываются только после проверок защитных признаков;
- изменение названия не создаёт новую операцию;
- исчезновение операции создаёт признак удаления из актуального снимка, но не физическое удаление;
- накопленный факт двух недель не суммируется.

### Статусы

- выбранная дата, равная `R3`, относится к фактической области; дата позже `R3` — к плановой;
- неполные даты дают диагностику, а не ложное `Не начато`;
- объёмное отклонение не подменяет отклонение по срокам;
- без утверждённого правила `T / R` не окрашивает IFC;
- после утверждения отдельной модели проверяются нулевой, частичный, полный и превышающий факт.

### IFC-маппинг

- КФО без корпуса и этажа не создаёт автоматическую связь;
- одна работа сохраняет все входящие операции отдельно;
- один IFC-элемент относится только к одной работе;
- отсутствие КФО `204.02.02.02` в XLSX оставляет соответствующие элементы IFC несвязанными;
- непроверенная таблица `секция → корпус` не участвует в производственном маппинге;
- после изменения правила связи пересчитываются без изменения исходных снимков.

## 15. Рекомендуемый порядок реализации

1. Реализовать парсер контракта XLSX и отчёт диагностик.
2. Добавить неизменяемые версии и хранение исходных значений, формул и накопленных измерений.
3. Подтвердить стабильность `A` на нескольких последующих выгрузках и реализовать реестр логических операций.
4. Согласовать смысл `O:P` и источник статуса.
5. Создать и наполнить справочник нормализации секций, корпусов и этажей.
6. Формировать работы графика и сравнивать покрытие с работами IFC.
7. Реализовать ручную проверку неоднозначных связей.
8. После утверждения статусной модели включить агрегацию на работу и окраску IFC.
