# SB_CDE — локальный рабочий контур

Единый локальный интерфейс объединяет три инструмента внутри тёмной оболочки КСУП BIM:

- **«ГВР»** — основной рабочий прототип SB_CDE для импорта графика выполнения работ, базовых и операционных версий и просмотра исходных операций;
- **«Карта» / Architecture Knowledge Graph** — служебный инструмент для просмотра актуальной архитектурной карты и изолированных драфтов задач;
- **IFC Viewer** — локальный read-only просмотр BIM-модели с вращением, панорамированием, масштабированием и стандартными видами.

Верхняя проектная навигация повторяет визуальный язык платформы, а рабочие инструменты «Мониторинг объекта», «ГВР» и «Архитектурная карта» вынесены в компактную горизонтальную строку вкладки BIM. Реализована только тёмная тема. «Мониторинг объекта» использует сводную IFC-модель как источник визуализации, но сама сводная модель не считается инструментом.

Это не три вкладки одной предметной модели. Данные графиков находятся в `data/schedules`, архитектурная карта — в `data/project.json` и `data/tasks`, а IFC-файл — в `public/models`; ни импорт графика, ни просмотр IFC не изменяют `CurrentMap`.

## Структура проекта

- `src/web/SchedulesApp.tsx` и `SchedulesPage.tsx` — основной frontend «ГВР»;
- `src/web/App.tsx` — отдельный read-only frontend архитектурной карты;
- `src/web/ProductShell.tsx` — тёмная оболочка КСУП BIM, проектная шапка, верхние вкладки и внутренняя BIM-навигация;
- `src/web/IfcViewer.tsx` — Three.js/web-ifc просмотрщик локальной BIM-модели;
- `public/models/` и `public/wasm/` — локальная IFC-модель и браузерный модуль её разбора;
- `src/server/` — единый локальный HTTP API с раздельными маршрутами и хранилищами;
- `src/shared/` — общие модели данных и схемы валидации;
- `data/` — актуальная карта, источники и изолированные драфты задач;
- `data/imports/schedules/` — входящая папка для локальных файлов графиков `.xml`;
- `data/schedules/` — управляемые копии исходных графиков и результаты их чтения;
- `data/ifc-kfo/bindings.json` — производное дерево КФО → корпус → секция → этаж → работа → IFC-элементы;
- `docs/features/` — спецификации функциональностей и шаблон ревью;
- `reports/` — воспроизводимые аналитические отчёты по локальным исходным данным;
- `tools/ifc-kfo/` — локальный генератор привязки IFC-элементов к работам графика;
- `tests/` — автоматические проверки;
- `archive/` — локальные исходные архивы, не входящие в Git;
- `build/` и `dist/` — генерируемые результаты сборки.

## Запуск

```bash
npm install
npm run dev
```

Откройте:

- http://localhost:5173/ — основной прототип «ГВР»;
- http://localhost:5173/architecture — служебная Architecture Knowledge Graph;
- http://localhost:5173/ifc — IFC Viewer.

Vite обслуживает обе frontend-поверхности, а Fastify поднимает общий локальный API на http://127.0.0.1:3001. Маршруты `/api/schedules/*` работают с графиками; `/api/project`, `/api/current-map` и `/api/tasks/*` — с архитектурной картой и драфтами.

Однопроцессный режим API: `npm start`. Проверки: `npm run check`, тесты: `npm test`, production-сборка: `npm run build`. Пересборка привязки IFC → КФО: `npm run build:ifc-kfo-bindings`.

## Работа через Agent Orchestrator

Репозиторий регистрируется в Orchestrator как самостоятельный Project. Для проекта рекомендуется указать:

- базовую ветку `main`;
- Codex как Worker и Orchestrator;
- `AGENTS.md` как Rules file;
- `npm ci` как Setup command.

В каждом worker создаётся отдельный Git worktree. Команда `npm run dev:ao` и файл `.ao/launch.json` запускают web и API на свободных локальных портах, поэтому параллельные preview не используют общие `5173`/`3001`. Внутри сессии preview открывается командой:

```bash
ao preview start
```

## Запуск в Docker

Docker нужен для воспроизводимого запуска без локальной установки Node.js: интерфейс и API собираются в один образ и работают на одном порту.

```bash
docker compose up --build
```

Откройте http://localhost:3001. Каталог `./data` примонтирован внутрь контейнера, поэтому задачи и драфты остаются в репозитории и переживают пересоздание контейнера. Остановка: `docker compose down`.

Контейнер предназначен для локального использования. Он не публикует приложение в интернет и не заменяет размещение исходников в GitHub. Для проверки production-режима без Docker доступны команды:

```bash
npm run build
npm run build:server
npm run start:prod
```

## Реализовано

### Общий runtime и API

- один локальный Fastify API и одна команда запуска для обоих интерфейсов;
- независимые маршруты, схемы и хранилища графиков проекта и архитектурных знаний;
- production-сервер раздаёт собранные frontend-маршруты и API на одном порту;
- общая тёмная оболочка КСУП BIM переключает «Мониторинг объекта», «ГВР» и «Архитектурную карту» в горизонтальной панели инструментов, сохраняя активную вкладку BIM;
- `Dockerfile` и `compose.yaml` сохраняют `data/` на хосте.

### IFC Viewer

- модель `RD_KR_04-08.ifc` загружается из локального репозитория и разбирается в браузере без внешнего API;
- Three.js-сцена поддерживает вращение ЛКМ, панорамирование ПКМ, масштаб колесом и кнопками;
- доступны возврат к модели и фиксированные виды ISO, сверху, спереди и справа;
- повторяющаяся геометрия отрисовывается инстансами, а IFC-код и Three.js загружаются отдельным route-chunk только на `/ifc`;
- интерфейс показывает контрольные счётчики элементов, геометрий и треугольников.

### Привязка IFC → КФО

- `data/ifc-kfo/bindings.json` хранит 622 конструктивных IFC-элемента с геометрией, `GlobalId`, `expressId` и Revit `tag` в иерархии КФО, корпуса, секции и этажа; пространственные атрибуты из XML-дерева используются для привязки только монолитных работ КФО `204.02.03.01` и `204.02.03.02`, отсутствующая в источнике секция остаётся `unknown`;
- все 305 объектов `IFCOPENINGELEMENT` (проёмы, отверстия и термовкладыши) исключены из результата;
- каждая пространственная работа содержит только отобранные по КФО модели операции XML, исходные `SourceStart`/`SourceFinish`, фактические даты, плановый/фактический объём, процент выполнения и вычисленный статус;
- статус рассчитывается воспроизводимо на дату состояния XML, а качество пространственного сопоставления сохраняется в `scheduleMatchLevel`;
- `data/ifc-kfo/statuses.json` — отдельный локальный справочник визуальных статусов: выполнено — зелёный, в работе — синий, запланировано — серый, неизвестно/нет работ — белый с opacity 40%;
- IFC Viewer получает привязки и справочник через read-only API, показывает всю геометрию модели и перекрашивает связанные элементы по статусу работы; элементы без работ используют статус по умолчанию с opacity 40%;
- временной ползунок ограничен датами связанных с моделью работ с календарным запасом ±1 месяц, меняет дату с шагом 3 дня и показывает месяцы с недельными засечками; для текущей уточнённой выборки диапазон составляет 30.06.2026–08.09.2027, а кнопка «Дата XML» возвращает фактический снимок на `2026-07-27`;
- отсутствующая в IFC секция записывается как `unknown`; балки и другие элементы без подтверждённой категории КФО сохраняются в диагностике как `unknown`, но полностью скрываются в IFC Viewer;
- генератор запускается вручную и не изменяет IFC, XML, `CurrentMap` или драфты других задач.

### Architecture Knowledge Graph

- типизированные и валидируемые модели `CurrentMap`, `Task`, `TaskDraft`, сущностей, связей и операций драфта;
- пустая актуальная карта с ревизией `R0`, каталог сущностей и read-only инспектор;
- граф на `@xyflow/react` с двойным визуальным кодированием: цвет обозначает конкретный тип, а форма — семейство объекта (компонент, процесс/скрипт/API, документ/файл, данные, справочник/решение); доступны силоподобная автораскладка, мини-карта, подсветка соседей, поиск и фильтры типов;
- узлы можно перетаскивать и возвращать к автораскладке; физика рассчитывается только для связного компонента перетаскиваемого узла и локально задетых соседей: связанные узлы передают импульс независимо от расстояния, а несвязанные реагируют только в малом радиусе (около 100 px); раскладка и инерционное панорамирование гарантированно останавливаются не позднее чем через 2 секунды после отпускания;
- связи выводятся без постоянных подписей на полотне: сплошная линия обозначает поток данных, штриховая — состав, пунктирная — зависимость; тип, описание, направление и основания выбранной стрелки показываются в read-only инспекторе; концы кривых автоматически следуют за формой узлов, но гарантированный обход всех узлов в MVP не выполняется;
- координаты и физика раскладки хранятся только в памяти открытого окна и не записываются в архитектурную модель;
- создание, удаление и связывание узлов через граф полностью отключены; доступны панорамирование, масштабирование, поиск, фильтрация и выбор;
- локальный API чтения проекта и сохранения документов задач/драфтов в `data/project.json` с атомарной заменой файла.

### ГВР

- сущность «График проекта» с неизменяемыми базовыми и операционными версиями: `Б1`, `О1.1`, `О1.2`, затем `Б2`, `О2.1` и т. д.;
- загрузка `.xml`, локальное сохранение источника каждой версии, распознавание исходных операций КСП, таблица, дерево и read-only карточка операции;
- специализированный разбор Microsoft Project `Project/Tasks/Task`: отдельные `UID`, `ID`, `Spider_Code`, исходный порядок, родительский UID, КФО/CBS и пользовательские поля через `FieldID → Alias`;
- метаданные проекта, показатели сроков/объёмов, связи `PredecessorLink` и отчёт валидации с SHA-256 и контрольными счётчиками;
- явное разделение исходной операции КСП и пользовательской проекции работ: экран работ вычисляемо отбирает только ветки СМР `Shell&Core` и `Fit-out (Служебные и технические помещения)`, а режим «Группы» строит read-only иерархию `КФО → корпус → этаж` без изменения исходного XML;
- поля `Start`/`Finish` сохраняются как даты из источника без автоматической трактовки как план или прогноз; плановое и прогнозное сопоставления остаются пустыми, `ActualStart`/`ActualFinish` сопоставлены фактическим полям источника;
- альтернативный импорт из папки `data/imports/schedules`: положите туда файл и нажмите в интерфейсе «Импортировать из папки»;
- тесты схем и отдельность драфта от `CurrentMap`.

## Ограничения архитектурной карты

Публикация, diff, импорт Markdown/`draft.json`, создание задач через UI, история ревизий и конфликты ещё не реализованы. UI не содержит операций изменения архитектурных узлов/связей. `data/project.json` — локальное демонстрационное хранилище; описанные в модели скрипты и интеграции не исполняются.

## ГВР

Откройте основной маршрут `/`. Сейчас все графики в интерфейсе относятся к единственному поддерживаемому типу — ГВР. Создать ГВР можно двумя способами:

1. создать график из первого базового XML — будет создана версия `Б1`;
2. добавить к выбранному графику операционный снимок или новую базовую версию;
3. либо положить файл в `data/imports/schedules/` и импортировать его без автоматического назначения типа.

Логический график сохраняется в `data/schedules/<scheduleId>/schedule.json`, а неизменённый XML каждой новой версии — в `data/schedules/<scheduleId>/versions/<versionId>/source.xml`. Операционная версия всегда ссылается на конкретную базовую. Любое обновление создаёт новый снимок и не переписывает предыдущий. Повторный импорт из входящей папки проверяется по SHA-256.

Для Microsoft Project импортёр читает задачи строго из `Project/Tasks/Task` в исходной последовательности. Для прочих XML сохраняется совместимый общий поиск узлов `Task`, `Activity`, `Operation`, `Work` или `Работа`. Все записи остаются **исходными операциями**, а не готовыми работами SB_CDE.

Проверка Microsoft Project включает уникальность `UID`, непрерывность `OutlineLevel`, согласованность `WBS` и `OutlineNumber`, полноту ожидаемых Alias и равенство числа найденных и сохранённых задач. В карточке доступны исходные поля, КФО/CBS, объёмы, сроки и UID предшественников.

Существующий импорт формата v1 читается совместимо и показывается как «Не классифицирован»: приложение не угадывает задним числом, был ли он базовым или операционным.

Текущие ограничения: фильтр веток и извлечение исходных названий корпуса/этажа жёстко заданы для эксперимента и не являются утверждённым системным классификатором; секция и вид работы в экранную группировку пока не включены, неоднозначные корпуса/этажи не нормализуются, показатели операций не агрегируются на уровне группы. Бизнес-прогноз не реализован, `EarlyStart/LateStart` не выдаются за прогноз. Ручная настройка соответствия XML-полей отсутствует; размер загрузки через UI ограничен 25 МБ. CSV/SQLite/XLSX из проверочного архива не являются отдельными источниками и в приложение не импортируются.

## VS Code: агенты «Прожарка» и «Регистратор ревью»

В `.github/agents/` установлены два custom agent для GitHub Copilot Chat:

- **Прожарка** критически проверяет выбранную спецификацию, процесс или интерфейс и не изменяет исходные файлы;
- **review-registrar** переносит уже сформулированные замечания и решения только в соседний `review-log.md`.

Чтобы подготовить ревью новой функциональности:

1. Скопируйте каталог `docs/features/_TEMPLATE` в `docs/features/<feature-name>`.
2. Замените `REPLACE_ME` в `spec.md` и `review-log.md` на один постоянный `artifact_id`.
3. Заполните `spec.md`, отделяя подтверждённые решения от гипотез и открытых вопросов.
4. В VS Code откройте Copilot Chat, выберите агента **Прожарка** и передайте ему `docs/features/<feature-name>/spec.md` вместе с `review-log.md`.
5. После проверки передайте результат агенту **review-registrar**, затем зафиксируйте свои решения по замечаниям.

Пример запроса: `Прожарь #file:docs/features/<feature-name>/spec.md. Учитывай review-log.md. Только новые существенные проблемы.` Команда `полная прожарка` запускает повторную проверку всех актуальных проблем. Доступность custom agents и их tool allowlist зависит от установленной версии VS Code и GitHub Copilot; локально в этом репозитории интеграция не проходила end-to-end проверку.

## SpiderProject UPD 2.1 — приоритет представлений

UPD 2.1 дополнительно сохранён в docs/sources/spiderproject-upd-2.1/; при противоречии с UPD 2.0 он имеет приоритет для пользовательской таблицы. Импорт сохраняет все XML-задачи без потерь. Экран «Работы» показывает только конечные обычные операции (activity) из разрешённых веток СМР; суммарные узлы, вехи и исключённые разделы в него не попадают. Для контрольного XML это 1 376 операций: 893 Shell&Core и 483 Fit-out служебных/технических помещений; 232 имеют КФО, 1 144 отображаются в группе «Без кода КФО». Режим «Группы» всегда группирует по КФО и позволяет включать/выключать уровни корпуса и этажа. «Дерево источника» остаётся отдельным read-only представлением всех XML-задач, строится строго по parentUid/parentId и sourceOrder; исходный вид показывает корень и первый уровень. Вехи сохраняются и учитываются отдельно; самостоятельная вкладка «Вехи» пока не реализована. Референсный export_user_work_rows.py — справочный скрипт и не запускается приложением автоматически.
