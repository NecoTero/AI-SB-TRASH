# UPD 2.0 — восстановление иерархии SpiderProject в SB_CDE

**Тип:** дополнение к текущим требованиям на импорт/просмотр XML-графика.  
**Статус:** проект технического задания на доработку; структура источника проверена на `down_PL_CON_13.xml`, реализация в SB_CDE не проверялась.  
**Приоритет:** P0 (верность дерева и данных), P1 (удобство просмотра).  
**Базовый артефакт:** `parse_msproject_xml.py` v1.0 + результат `works.sqlite`.  
**Новый артефакт:** `spider_treegrid_adapter.py` v2.0.

## 0. Короткая инструкция системе / ИИ-агенту

> Доработай отображение импортированного графика SpiderProject в существующем проекте SB_CDE. Не меняй источники бизнес-данных и не пересобирай классификатор работ. Используй уже извлечённые записи `tasks` из `works.sqlite` (или эквивалентные данные текущей БД). Восстанови **точное исходное дерево** по `parent_uid` и `source_order`, полученным при чтении `OutlineLevel` и последовательности `<Task>` в XML. Представь график в виде **иерархической таблицы (Tree Grid)**, где каждая задача — отдельная строка, суммарные узлы разворачиваются, а полный набор дат, объёмов и кодов доступен в колонках/карточке. У дерева не должно быть собственной логики группировки по КФО, CBS, текстовому имени или Spider_Code. Не удаляй промежуточные уровни, не объединяй одинаково названные работы, не заполняй отсутствующие поля догадками и не суммируй объёмы без бизнес-правила. В БД первичный ключ записи версии: `(platform_project_id, snapshot_id, uid)`. `WBS` — отображаемый путь, `Spider_Code` — код операции, оба не являются уникальными ключами. Не завершай до прохождения критериев приемки ниже.

## 1. Цель доработки

**Сейчас:** пользователь видит плоский/неправильно сгруппированный набор работ, который не совпадает со структурой SpiderProject.

**Должно стать:** в текущем проекте пользователь видит одну иерархическую таблицу графика из исходного файла. В дереве сохранены:

1. Все уровни от корневой задачи до конечных операций (и промежуточные суммарные узлы).
2. Отношения «родитель → непосредственный ребёнок».
3. Исходный порядок строк.
4. Одинаково названные задачи как отдельные записи.
5. Плановые, фактические и дополнительные даты/объёмы на соответствующих записях без подстановок.
6. Независимые классификационные поля «Код проекта», «Код CBS», «Код КФО».

Никакой отдельный выбор проекта при входе во вьювер не нужен: `platform_project_id` берётся из контекста уже открытого проекта SB_CDE. **Важно:** `platform_project_id` — идентификатор проекта платформы, а `project_code` — значение из XML; не смешивать их.

## 2. Установленные факты об образце XML

Формат: XML с корнем `Project`, namespace `http://schemas.microsoft.com/project`; задачи находятся в `/Project/Tasks/Task` **последовательно, не вложены физически друг в друга**.

| Показатель в `down_PL_CON_13.xml` | Проверенное значение |
|---|---:|
| Все `<Task>` | 3 134 |
| Суммарные задачи (`Summary=1`) | 744 |
| Несуммарные задачи (`Summary=0`) | 2 390 |
| Максимальный `OutlineLevel` | 8 |
| Корневых задач | 1 |
| Непосредственных веток корня | 8 |
| Задач с `Код CBS` | 283 |
| Задач с `Код КФО` | 284 |
| Задач с плановым объёмом `SP_VolPlan` | 1 923 |
| Задач с фактическим объёмом `SP_VolFact` | 473 |

На первом уровне под корнем: «Концепции», «Разработка ПД», «Разработка РД», «МТО», «СМР», «ПНР», «ЗОС», «РВ». Это **только результат чтения конкретного файла, не зашитая структура всех проектов**.

## 3. Источник правды и последовательность обработки

```text
Исходный XML SpiderProject
    │
    ▼
parse_msproject_xml.py (существующий скрипт)
    │  читает Task, ExtendedAttributes, даты/объёмы
    │  рассчитывает parent_uid по OutlineLevel и порядку
    ▼
works.sqlite: tasks + project_meta + parse_report
    │
    ▼
spider_treegrid_adapter.py (данный UPD)
    │  нормализует контракт API, добавляет version-aware row_id
    │  проверяет связи и не меняет значения источника
    ├─ treegrid_rows.json — плоская коллекция (основной источник UI)
    ├─ treegrid_tree.json — эквивалентное вложенное дерево
    ├─ treegrid_manifest.json — источник/версия/контекст проекта
    └─ treegrid_validation.json — результаты проверок
    │
    ▼
БД SB_CDE → API → Tree Grid внутри открытого проекта
```

**Не нужно повторно парсить XML внутри фронтенда.** Внутренняя БД должна хранить ссылки «родитель/ребёнок», а дерево для интерфейса восстанавливается из этих ссылок. JSON-дерево — представление; не вторая независимая бизнес-сущность.

## 4. Обязательная модель данных

**Сущность `schedule_snapshot` (версия импортированного графика)**:

| Атрибут | Назначение |
|---|---|
| `platform_project_id` | Текущий проект платформы, присваивает SB_CDE |
| `snapshot_id` | SHA-256 исходного XML; идентификатор содержимого версии |
| `source_filename` | Название файла |
| `source_revision` | `Project/Revision`, если есть |
| `source_status_date` | `Project/StatusDate`, если есть |
| `imported_at` | Время фактического импорта, задаёт платформа (не брать из графика) |

**Сущность `schedule_task` (одна строка = один `<Task>`)**:

| Атрибут | Источник / требование |
|---|---|
| `platform_project_id`, `snapshot_id`, `uid` | Составной ключ задачи **внутри версии графика** |
| `row_id` | Строковый ID вида `snapshot_id:uid`, для клиентского Tree Grid; в платформе с нескольких проектов использовать и `platform_project_id` |
| `parent_uid` / `parent_row_id` | Непосредственный родитель (nullable только для корня) |
| `source_order` | Номер позиции `<Task>` начиная с нуля, НЕ сортировать по UID или WBS |
| `id` | Исходный `Task/ID`, отдельно от UID |
| `task_name` | `Task/Name`, без корректировки текста |
| `task_code` | Пользовательский атрибут с alias `Spider_Code` |
| `work_code_pir` | Пользовательский alias `Код работ из раздела ПИР` |
| `wbs` | `Task/WBS` **строка** (включая точки/нули) |
| `outline_number`, `outline_level` | `Task/OutlineNumber` и `Task/OutlineLevel` |
| `is_summary`, `is_milestone` | `Task/Summary` и `Task/Milestone` |
| `project_code` | Расширенный атрибут по alias `Код проекта` |
| `cbs_code`, `cbs_name` | `Код CBS` и `CBS` |
| `kfo_code`, `kfo_name` | `Код КФО` и `КФО` |
| `plan_start`, `plan_finish` | `Task/Start`, `Task/Finish`; текущие даты, **не утверждённый baseline** |
| `actual_start`, `actual_finish` | `Task/ActualStart`, `Task/ActualFinish` |
| `early_start`, `early_finish`, `late_start`, `late_finish` | Соответствующие теги `Task` |
| `constraint_date`, `deadline`, `stop_date`, `resume_date` | Дополнительные даты из Task, если представлены |
| `volume_plan`, `volume_fact` | `SP_VolPlan`, `SP_VolFact` |
| `percent_complete` | `PercentComplete` (из XML, не пересчитывать) |
| `volume_cost` | `SP_VolCost` — **не физический объём**, сохранять отдельно |
| `duration`, `actual_duration`, `remaining_duration` | Исходные продолжительности `PT...` без произвольного пересчёта |
| `source_attributes` | Прочие теги Task и расширенные поля как исходные значения |
| `nested_xml_json` | Вложенные данные, если встречаются |

**Поля даты:** сохранять исходный текст ISO без выдуманного часового пояса.  
**Точные числа:** значения планового/фактического объёма в API передавать в строковой десятичной форме исходного XML; в постоянной БД при необходимости использовать `DECIMAL`/`NUMERIC`, а не двоичные приближённые расчёты.  
**Пропуски:** `NULL` (или `null` в JSON), `0` остаётся нулём. **Не наследовать** CBS/КФО от родителей.  
**Физические единицы измерения:** не подставлять м³, м² или шт., если они не определены в источнике/отдельном справочнике с подтверждённой связью.

### Пользовательские атрибуты

Соответствия искать не по жёстко заданным `FieldID` в коде, а по словарю `/Project/ExtendedAttributes/ExtendedAttribute`:

```text
Alias "Код проекта" → project_code
Alias "Код CBS"     → cbs_code
Alias "CBS"         → cbs_name
Alias "Код КФО"     → kfo_code
Alias "КФО"         → kfo_name
Alias "Spider_Code" → task_code
Alias "Код работ из раздела ПИР" → work_code_pir
```

Для **этого** файла проверено: Spider_Code `188744016`; Код проекта `188743737`; Код CBS `188743749`; Код КФО `188744009`. В иных файлах ориентироваться на `Alias`, не предполагать постоянство `FieldID`.

## 5. Строгое правило восстановления дерева

Приоритетом для **готовой базы** являются `parent_uid` + `source_order`. Если читается **оригинальный XML**, родитель устанавливается обходом последовательных Task и `OutlineLevel` (стеком). Значение WBS используется для отображения и дополнительной проверки. Если WBS неконсистентен, не «чинить» молча, а выдавать диагностику.

```text
rows = ORDER BY source_order ASC
index = { uid -> row }
roots = []
for row in rows:
    if row.parent_uid IS NULL:
        roots.append(row)
    else:
        assert row.parent_uid in index
        index[row.parent_uid].children.append(row)
```

Раскрываемость определяется **наличием дочерних записей** (`has_children`), но `Summary` хранится отдельно. В дереве не пропускаются суммарные задачи, вехи, задачи с пустыми кодами/объёмами. **Не отбирать только листья.**

**НЕЛЬЗЯ:**

- группировать дерево по CBS, КФО, WBS-префиксам или названиям вместо фактического `parent_uid`;
- объединять одинаковые названия, одинаковые WBS между версиями или одинаковые `Spider_Code`;
- использовать `ID`, `WBS`, `Spider_Code` или имя вместо составного ключа задачи;
- сортировать ветки по алфавиту, коду КФО, CBS или числовому WBS;
- строить работу заново из кусочков кода WBS, если связь уже есть;
- дублировать суммарный объём и сумму объёмов листьев как независимые объёмы для общего итога;
- вычислять статусы, план-факт, объёмы или фактические даты, которых нет в файле.

## 6. Требования к интерфейсу (Tree Grid)

**P0 — обязательно**

1. В существующем экране проекта показать график как единую таблицу с раскрываемыми строками.
2. Первая колонка: раскрытие/сворачивание, визуальный отступ уровня, WBS, имя работы; рядом отдельная колонка `Spider_Code`.
3. На старте отображать корневую задачу и восемь веток первого уровня (для проверяемого образца). Внутренние ветви допускается сворачивать по умолчанию.
4. У суммарной задачи показывать стрелку раскрытия, если есть дочерние записи; у листа стрелки нет. Не создавать псевдо-группы «CBS» / «КФО».
5. Отображать `UID`/технический ID по запросу, WBS, тип, коды проекта/CBS/КФО, начало/окончание, факт-начало/факт-конец, плановый/фактический объём, процент выполнения.
6. В карточке работы показать оставшиеся даты, объёмно-стоимостные и исходные дополнительные поля (без потери).
7. Пустое значение визуально `—` и в данных `null`; `0` показывать как `0`.
8. Переход к работе/поиск по коду или наименованию раскрывает всех её предков, не перемещая строку.
9. При обновлении версии графика считать её новым `schedule_snapshot`; исходный XML/старую версию не перезаписывать. Новую актуальную версию выбирает логика платформы, а не парсер.

**P1 — удобство (не блокирует P0):** «развернуть до уровня N», «свернуть всё», запоминание раскрытых узлов для открытой версии, фильтры по CBS/КФО без изменения родительских связей, экспорты видимой ветки.

### Предлагаемая конфигурация колонок

Первая группа — дерево: `WBS`, `Наименование`. Затем: `Код работы (Spider_Code)`, `Тип`, `Код проекта`, `Код CBS`, `Код КФО`, `Начало`, `Окончание`, `Факт начала`, `Факт окончания`, `Плановый объём`, `Фактический объём`, `% выполнения`. Остальные даты и показатели открываются в подробностях, но должны быть в данных.

### Конкретный контрольный пример

В XML есть разные записи:

```text
WBS 1.1.1    | UID=4 | Name=CP | Summary=1
  WBS 1.1.1.1 | UID=5 | Name=CP | Summary=0 | Spider_Code=113190265
```

Они не должны склеиваться в одну работу. Аналогичные пары встречаются в разделе СМР.

## 7. Контракт передачи на фронтенд

Используйте готовый `treegrid_rows.json` либо отдавайте такие же поля своим API. Минимальный пример **структуры** (идентификаторы условны; значения полей взяты из образца):

```json
{
  "platform_project_id": "<id текущего проекта SB_CDE>",
  "snapshot_id": "<sha256 исходного XML>",
  "uid": 5,
  "parent_uid": 4,
  "source_order": 4,
  "wbs": "1.1.1.1",
  "outline_level": 4,
  "task_name": "CP",
  "task_code": "113190265",
  "node_type": "task",
  "has_children": false,
  "volume_plan": "100",
  "volume_fact": null
}
```

`treegrid_rows.json`: `{ "manifest": {..}, "rows": [..] }`. Каждый `rows[i]` включает названные поля, `row_id`, `parent_row_id`, `source_attributes` и все дополнительные даты.  
`treegrid_tree.json`: `{ "manifest": {..}, "tree": [{ "work": {..}, "children": [...] }] }` — та же совокупность задач с теми же свойствами, но вложенная. **Не импортировать плоский и вложенный набор как два отдельных набора задач**.

Список REST/GraphQL endpoint-ов и миграции физической схемы БД необходимо адаптировать под стек уже существующей платформы. Скрипт **не внедряет изменения в SB_CDE**, он подготавливает воспроизводимые данные и подтверждает контракт.

## 8. Версии, идентификаторы и повторный импорт

- `UID` уникален внутри проверяемой выгрузки, но **сам по себе не является глобальным ключом**; использовать `(platform_project_id, snapshot_id, uid)`.
- `snapshot_id` — SHA-256 байтов исходного файла. Повторный импорт того же содержимого в тот же проект должен быть **идемпотентным**.
- `Project/Revision` хранится как метаданные, но отдельно от хэша; сам номер Revision может повторяться у разных содержимых.
- Соответствие «это та же работа между версиями графика» **не выводить автоматически по UID/Spider_Code/WBS**: это отдельная бизнес-задача на сопоставление версий.
- Если задачи нет в новой версии, не удалять её из архивной версии. Не подменять старые факты текущими.

## 9. Приёмочные критерии

**Для любого корректного нового XML:**

- [ ] Количество импортированных строк = количеству XML `<Task>`.
- [ ] Количество узлов в дереве = количеству строк.
- [ ] Каждая запись встречается в дереве ровно один раз.
- [ ] Ни у одной некорневой записи нет отсутствующего родителя.
- [ ] `parent_uid`, `source_order`, `wbs`, `outline_level`, `uid` не изменены.
- [ ] Порядок непосредственных дочерних задач совпадает с порядком XML.
- [ ] Пустые коды/даты/объёмы остались пустыми; исходные нули остались нулями.
- [ ] Суммарные задачи и вехи представлены без объединения с детьми.
- [ ] Идентичные названия и повторяющиеся Spider_Code не схлопываются.
- [ ] Плоская таблица и Tree Grid ссылаются на одни и те же задачи одной версии.
- [ ] При фильтрации/поиске сохраняются реальные родители найденных строк.
- [ ] Актуальная версия и история импорта не смешиваются.

**Для контрольного файла `down_PL_CON_13.xml`:**

- [ ] Ровно 3 134 задачи в таблице и 3 134 узла в дереве.
- [ ] 744 суммарных и 2 390 несуммарных задач.
- [ ] Одна корневая задача; восемь непосредственных веток; максимальный уровень 8.
- [ ] Пара WBS 1.1.1 / 1.1.1.1 видна как родитель и дочерняя операция.
- [ ] Данные CBS, КФО, план/факт объёмов не появлялись на задачах, где в XML они отсутствуют.

## 10. Локальный запуск и артефакты

Положите `parse_msproject_xml.py`, `spider_treegrid_adapter.py` и XML рядом либо укажите полные пути.

```powershell
# 1. Уже существующий парсер XML
py -3 parse_msproject_xml.py "down_PL_CON_13.xml" --out "parsed"

# 2. Новый UPD-адаптер для иерархической таблицы
py -3 spider_treegrid_adapter.py --db "parsed/works.sqlite" --platform-project-id "<ID проекта из платформы>" --out "treegrid"

# 3. Самопроверка (можно использовать прежнюю уже готовую БД)
py -3 test_treegrid_contract.py --db "parsed/works.sqlite" --folder "treegrid"
```

**Результат:** `treegrid_rows.json`, `treegrid_tree.json`, `treegrid_manifest.json`, `treegrid_validation.json`. JSON можно подавать в тестовый Tree Grid или адаптировать под свой API.  
**Внимание:** `--platform-project-id` передаёт вызывающая система; код проекта из XML не может автоматически заменить этот идентификатор.

## 11. Границы данной доработки

В рамках UPD 2.0 **не разрабатываем** новые статусы СМР/закупки, 4D/5D-таймлайнер, сравнение редакций, расчёт фактических объёмов, вычисление суммарного прогресса и правила связывания с BIM-моделью. Цель UPD — точное структурное отображение уже импортированных работ.

**Проверено:** формат XML, количество записей, поля, исходная иерархия и сформированные файлы.  
**Не проверено:** реальное отображение SpiderProject на пользовательском компьютере и технологии/архитектура БД SB_CDE. Сама платформа после подготовки файлов не изменяется автоматически.
