# UPD к реализации импорта и просмотра графика SpiderProject

**Задача:** исправить отображение графика работ, импортированного из XML SpiderProject, в существующем проекте SB_CDE. Сейчас график превращается в неправильный плоский или произвольно сгруппированный список. Необходимо восстановить визуальную иерархию исходного графика в виде **раскрываемой таблицы (Tree Grid)**. Не делать новый классификатор и не переделывать данные в произвольную структуру.

**Основа:** предыдущий парсер `parse_msproject_xml.py` уже создал `works.sqlite` с таблицей `tasks`. Здесь есть все нужные поля: `uid`, `parent_uid`, `source_order`, `wbs`, `outline_level`, `is_summary`, `is_milestone`, `task_name`, `task_code`, `project_code`, `cbs_code`, `kfo_code`, даты и объёмы. Для UI использовать существующий результат импорта; повторно придумывать способ парсинга не требуется. Готовый адаптер `spider_treegrid_adapter.py` создаёт `treegrid_rows.json` и `treegrid_tree.json`.

## Правила, которые требуется реализовать

1. **Одна строка БД = одна исходная задача `<Task>`**, включая корень, суммарные задачи, операции и вехи. Не удалять промежуточные уровни, не склеивать одинаковые названия.
2. **Строить дерево исключительно по `parent_uid`**, порядок дочерних элементов — исключительно по `source_order`. `WBS` и `outline_level` сохранять для отображения/валидации. Не группировать исходное дерево по CBS, КФО, названию, Spider_Code и не сортировать по алфавиту.
3. **Ключ задачи в платформе:** `(platform_project_id, snapshot_id, uid)`, где `platform_project_id` — текущий проект SB_CDE, `snapshot_id` — SHA-256 исходного XML. `Spider_Code` — атрибут `task_code`, не уникальный идентификатор; `WBS` — путь в графике, не PK.
4. **Интерфейс:** настоящая иерархическая таблица с раскрытием/сворачиванием строк, WBS + наименование, отдельными кодами проекта/CBS/КФО и кодом работы, датами начала/окончания и факта, плановым/фактическим объёмами и процентом. Остальные исходные даты/объёмы доступны в подробностях задачи.
5. **Сохранять NULL отдельно от нуля.** Отсутствующие коды, даты и объёмы не додумывать, не наследовать от родителей, не пересчитывать. `SP_VolCost` не считать физическим объёмом, `Start/Finish` не объявлять утверждённым базовым планом.
6. **Суммарная задача остаётся отдельным узлом**, а не суммой или копией дочерних. Не складывать объёмы суммарных задач и операций без отдельного правила, учитывающего единицы измерения.
7. **Поиск** по названию, WBS, Spider_Code раскрывает путь к найденной работе (все её предки), но не меняет структуру графика. Фильтры КФО/CBS не переподчиняют задачи.
8. **Версии:** повторный импорт того же файла в тот же проект не создаёт дублирующую версию; новые содержимое/хэш сохраняются отдельным снимком. Сопоставление одной работы между редакциями — отдельная задача, не выполнять по догадке.

## Проверка результата на `down_PL_CON_13.xml`

- 3 134 узла/строки, 744 суммарных, 2 390 несуммарных; максимальный OutlineLevel = 8.
- Один корень `МАН16_Гостиница5_2`, восемь непосредственных веток: Концепции, Разработка ПД, Разработка РД, МТО, СМР, ПНР, ЗОС, РВ.
- `UID=4`, WBS `1.1.1`, «CP» — родитель; `UID=5`, WBS `1.1.1.1`, «CP» — дочерняя операция. **Должны остаться двумя строками**.
- Количество задач, связи родителей, порядок и исходные значения должны совпадать с XML/`works.sqlite`. В журнале проверки нет критических ошибок.

**Реализация и контракт:** `UPD_2_0_SpiderProject_TreeGrid.md`, `spider_treegrid_adapter.py`, `queries_for_treegrid_SQLite.sql`, `test_treegrid_contract.py`. Не считать задачу завершённой без прохождения приёмочных проверок.

**Границы:** не разрабатывать в рамках этого UPD статусы, 4D/5D, прогнозы, связь с BIM и алгоритм сопоставления версий. Визуальное тождество реальному экрану SpiderProject можно окончательно подтвердить только сравнением с ним, а не только с XML.
