# UPD 2.1 — пользовательская таблица работ и иерархия SpiderProject

**Статус:** дополнение к `UPD_2_0_SpiderProject_TreeGrid.md`. При противоречии правил о строках пользовательской таблицы приоритет имеет UPD 2.1. Исходный XML, парсер, архив БД и логика иерархии остаются без изменений.

## 1. Ключевое уточнение

**Таблица работ — это построчное представление конечных работ, а не отражение всех узлов XML.** В ней не должны появляться строки с корнем проекта и суммарными/группирующими задачами. Иерархия (дерево) является отдельным описанием положения каждой работы в графике.

Логическое разделение:

- **Слой хранения:** все `<Task>` из XML, включая корень, суммарные задачи, конечные операции и вехи. Без потерь. Один исходный `<Task>` = одна запись в техническом хранилище.
- **Пользовательская таблица «Работы»:** каждая строка = одна конечная операция; строки-суммарные задачи не показывать. В предлагаемом варианте вехи не считать работами и в этой таблице не показывать; отдельно хранить и при необходимости выводить во вкладке «Вехи». **Это правило для вех подлежит подтверждению владельцем продукта.**
- **Представление «Дерево»:** узлы группировки показывать для навигации и восстановления исходного пути; конечные работы — листовые узлы. Каждая строка таблицы ссылается на полный путь в дереве.

## 2. Источник данных

Использовать имеющуюся `works.sqlite` / таблицу `tasks` (результат `parse_msproject_xml.py`) и поля:

- `uid` — технический идентификатор в рамках импортированного снимка;
- `parent_uid` — непосредственный родитель;
- `source_order` — порядок в XML;
- `wbs` — код структуры;
- `outline_level` — исходная глубина;
- `is_summary` — суммарная задача (1) / несуммарная (0);
- `is_milestone` — веха (1) / обычная операция (0);
- `task_name`, `task_code`, `project_code`, `cbs_code`, `kfo_code`;
- плановые, фактические, ранние, поздние и прочие даты, `volume_plan`, `volume_fact`, `percent_complete`, а также исходные дополнительные поля.

Не строить пользовательскую таблицу непосредственно из сырого XML и не выводить автоматически все поля `xml__*`, `nested_xml_json`, системные параметры проекта и календарей.

## 3. Применяемое правило отбора пользовательских строк

В контрольной SQLite:

```sql
SELECT *
FROM tasks
WHERE is_summary = 0 AND COALESCE(is_milestone, 0) = 0
ORDER BY source_order;
```

Это **конечные операции**, а не все XML-задачи.

Результат на `down_PL_CON_13.xml`:

- 3 134 XML-задачи всего (храним все);
- 744 суммарные задачи (используем в дереве, не выводим отдельными строками таблицы работ);
- 1 949 обычных конечных операций (строки пользовательской таблицы «Работы»);
- 441 веха (храним; отдельно определяем, нужны ли в основной таблице или во вкладке «Вехи»).

Если продуктовая договорённость будет **«вехи включать в общий список работ»**, правило меняется на `WHERE is_summary = 0` и таблица содержит 2 390 строк. До согласования не путать «конечная операция» с «любой несуммарной задачей».

## 4. Поля одной строки пользовательской таблицы

Основные колонки по умолчанию (порядок может настраиваться пользователем):

1. WBS;
2. Наименование работы;
3. Код работы `task_code` (исходно Spider_Code);
4. Код проекта;
5. Код CBS;
6. Код КФО;
7. Начало `plan_start` / Окончание `plan_finish` — **текущие даты графика**, не утверждённый baseline;
8. Факт. начало `actual_start` / Факт. окончание `actual_finish`;
9. Плановый объём `volume_plan` / Фактический объём `volume_fact`;
10. Выполнение, % `percent_complete`;
11. Путь по дереву (`hierarchy_path`) — по запросу/как дополнительная колонка или в карточке.

Прочие даты и объёмы из XML доступны в деталях работы, не засоряют базовую таблицу. Если поле отсутствует в XML — оставить NULL, **не** подменять нулём или значением родителя.

## 5. Как устроена связь с деревом

У каждой конечной операции сохранять `parent_uid`, `wbs`, `outline_level` и рассчитанный **без изменения XML** список её предков `ancestors` от корня до непосредственного родителя: `[{uid,wbs,task_name,outline_level}, ...]`.

Дерево строится только по `parent_uid`, порядок — только по `source_order`, без группировки/пересортировки по CBS, КФО или наименованию. Суммарные узлы присутствуют **только как структурные узлы**, а не как дополнительные пользовательские работы.

Важно: совпадающие названия и `task_code` не основание для объединения; идентификатор внутри платформы — `(platform_project_id, snapshot_id, uid)`.

## 6. Критерии приёмки

1. Хранилище сохраняет 3 134 задачи, включая 744 суммарные и 441 веху.
2. Пользовательская таблица «Работы» содержит **1 949** строк, не содержит `is_summary=1` и `is_milestone=1`, пока правило вех не изменено.
3. В пользовательской таблице нет дополнительных строк «СМР», «МТО», «Подготовительный период», корня проекта и других структурных групп.
4. У каждой строки работ есть корректный `uid` и `parent_uid`, исходные даты, объёмы и коды.
5. По каждой строке можно восстановить непрерывную цепочку родителей до корня и подсветить работу в дереве.
6. Поиск/фильтрация в таблице не ломают дерево и не создают дубликаты.
7. Пользовательские колонки не показывают служебные `xml__*` и JSON/метаданные, но данные остаются доступными на техническом уровне.

## 7. Реализация

Референсный скрипт `export_user_work_rows.py` читает существующую `works.sqlite` **без изменения** и формирует:

- `works_ui_rows.csv` — лёгкая плоская таблица только конечных операций;
- `works_ui_rows.json` — те же работы с массивом `ancestors` и полным `hierarchy_path`.

Запуск:

```bash
python export_user_work_rows.py msproject_parser/result/works.sqlite --out result_ui
```

### Изменение к предыдущему UPD 2.0

В UPD 2.0 фразу «показать все 3 134 задачи в таблице Tree Grid» считать **требованием к полноте исходного дерева/техническому хранилищу, а не к плоской пользовательской таблице «Работы»**. Пользовательская таблица — отфильтрованная проекция без служебных узлов. Отображение иерархии и табличная выборка используют один источник данных.
