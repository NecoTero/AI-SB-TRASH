# PROJECT_SPEC.md — Architecture Knowledge Graph

> Версия: 0.2 — продуктовая спецификация для старта разработки.  
> Язык интерфейса и документации: русский; язык технических идентификаторов и кода: английский.  
> Название `Architecture Knowledge Graph` — рабочее.  
> Описываем проектируемое приложение, **не подтверждённую фактическую архитектуру** SB_CDE.

## 1. Цель

Создать «живую карту» архитектурных знаний для бизнес-аналитика. При проработке нового или существующего функционала аналитик изучает документы, данные, источники, компоненты, скрипты, API и их связи. По мере работы собирается **драфт архитектурных изменений в рамках конкретной задачи**. После завершения разработки пользователь может запросить актуализацию либо система предложит её. Только после просмотра и **явного подтверждения пользователя** изменения драфта переходят в **единую актуальную карту**.

Система не обязана описывать всю корпоративную архитектуру, физические серверы и исходный код. На карте допустимы реальные, предполагаемые и ещё не исследованные объекты с понятным указанием степени определённости.

### Главная концепция

- **Актуальная карта** — единый опубликованный граф архитектурных знаний.
- **Драфт задачи/функциональности** — отдельная версия *предлагаемых изменений* относительно конкретной ревизии актуальной карты.
- **Граф** — *только отображение*. Нет ручного графического редактирования ни в актуальной карте, ни в драфте.
- **Изменение содержимого** — через описание задачи, исходные материалы и формирование структурированных операций (на старте — с помощью Codex в VS Code), а не рисование мышью.
- **Актуализация** — осознанное отдельное действие, происходящее **после** проверки драфта. Предложение актуализировать карту никогда не применяет изменения само.

```text
                           ┌────────────────────────┐
                           │ Актуальная карта (R7)  │
                           │ CurrentMap             │
                           └────────────┬───────────┘
                                        │ базовая ревизия
                     ┌──────────────────┼────────────────────┐
                     ▼                  ▼                    ▼
             ┌────────────┐    ┌────────────┐       ┌────────────┐
             │ Драфт A    │    │ Драфт B    │       │ Драфт C    │
             │ Задача A   │    │ Задача B   │       │ Задача C   │
             └─────┬──────┘    └────────────┘       └────────────┘
                   │ предпросмотр + diff
                   ▼
             Явное подтверждение пользователя
                   │
                   ▼
             Валидация + проверка конфликтов
                   │
                   ▼
             Актуальная карта (R8)
```

Схема иллюстративная: пока драфт A публикуется, драфты B и C не меняются. Для их публикации может потребоваться проверка совместимости с R8.

## 2. Термины и разграничения

| Термин | Смысл |
|---|---|
| `CurrentMap` / актуальная карта | Опубликованная совокупность сущностей и отношений с номером ревизии. |
| `Task` / задача | Единица аналитической/проектной работы над функциональностью. Имеет `taskId`, название, описание, статус. |
| `TaskDraft` / драфт | Набор предлагаемых операций по одной задаче, привязанный к исходной ревизии карты. |
| `DraftPreview` / предпросмотр | Вычисленная карта «как будет выглядеть после этого драфта», отдельно от `CurrentMap`. |
| `ChangeOperation` | Добавление, изменение или архивация сущности/связи, предлагаемая в драфте. |
| `MapRevision` | Зафиксированная история опубликованных изменений актуальной карты. |
| `Entity` | Архитектурный объект с уникальным стабильным ID. |
| `Relation` | Типизированная направленная или ненаправленная связь между объектами. |
| `View` | Способ отображения выбранной части карты: фильтры, группировка, автоматическая раскладка. |
| `Zone` | Абстрактная функциональная/информационная область для группировки объектов «облаком». |
| `Artifact` | Данные или логическая структура данных, не обязательно файл. |
| `Evidence` | Основание: требование, документ, раздел, решение, ссылка или текстовое пояснение. |

**Важное разделение состояний:**

- `draftStatus` — в каком состоянии **предложение по изменению карты**: черновик, готов к проверке, опубликован, отклонён, конфликтующий.
- `implementationStatus` — в каком состоянии **реальная разработка функциональности**: неизвестно, проектируется, в работе, завершена и т. п.
- `architectureState` — известно ли, что **сама сущность** реально существует: `existing`, `proposed`, `unknown`, `retired`.
- Публикация архитектурного драфта не меняет два последних статуса автоматически и не утверждает, что код функциональности внедрён.

## 3. Две архитектурные области

### 3.1. Актуальная карта (`CurrentMap`)

Это **один канонический** граф для всего проекта:

- содержит только опубликованные объекты и связи;
- сохраняет ревизию, историю и ссылки на задачи-источники изменений;
- служит основой для всех драфтов;
- не допускает редактирования через UI графа, карточки объектов или обычные команды изменения;
- меняется **только через атомарную публикацию валидного драфта** после явного подтверждения.

«Актуальная» означает **актуальная согласованная карта знаний**, а не гарантированно актуальное состояние кода или продакшен-среды.

### 3.2. Драфты задач (`TaskDraft`)

У каждой задачи/функциональности **свой независимый драфт**:

- `taskId` обязателен; каждая задача имеет **не более одного активного драфта** одновременно;
- драфт содержит `baseRevision` и набор предлагаемых операций над сущностями и связями;
- в ходе проектирования драфт может неоднократно дополняться и пересобираться;
- драфт может ссылаться на существующие объекты и создавать новые;
- объекты другого активного драфта не считаются частью опубликованной карты;
- драфт не меняет `CurrentMap` даже при `implementationStatus = completed`;
- пользователь может смотреть `DraftPreview` как самостоятельную карту, но не редактирует её мышью;
- после публикации остаётся история драфта, связанная с ревизией карты; дальнейшие изменения той же функциональности оформляются новой задачей или новым циклом драфта, без изменения опубликованной истории.

Возможна привязка нескольких задач к одной функциональности (`featureId`), но драфты остаются отдельными по `taskId`.

### 3.3. Откуда появляются данные драфта

**В MVP — не из ручного графического редактора.** Пользователь формулирует задачу/требования в Markdown, прикладывает/ссылается на материалы, обсуждает решения с Codex. Codex предлагает содержимое `draft.json`: операции, связи, причины изменения и поля `unknown` для пробелов. Приложение валидирует и показывает предложение.

Потенциальный будущий вариант — встроенный чат для формирования драфта и извлечение данных из документов, но **не реализовывать без отдельного задания**. Приложение должно работать без ключей LLM, платных API и внешней сети.

Текст задачи редактировать можно; **карту — нельзя**. Исправление неточного драфта происходит через уточнение задачи/команду Codex и повторное формирование операций, а не через перетаскивание или правку узла.

## 4. Основные пользовательские сценарии

### Сценарий A. Разработка новой функциональности

1. Создать задачу с уникальным ID и названием (например, `TASK-001`).
2. Зафиксировать описание, ограничения, решения, ссылки на документы; открыть актуальную карту для анализа существующих объектов.
3. Сформировать драфт задачи. Codex находит подходящие ID существующих объектов и описывает добавления/изменения/архивацию связей в `draft.json`.
4. Открыть `DraftPreview`. На графе видны текущие объекты и предлагаемые изменения с различимыми метками.
5. В ходе разработки уточнять материалы и **перегенерировать/обновлять драфт** без изменения актуальной карты.
6. По окончании разработки пометить задачу завершённой или оставить её в работе.
7. Если задача завершена, приложение **предлагает** «Актуализировать карту?»; пользователь также может начать процедуру сам независимо от статуса задачи.
8. Пользователь открывает diff и отдельно подтверждает или отклоняет публикацию.
9. При успешной публикации создать новую ревизию `CurrentMap`, отметить драфт опубликованным и сохранить связь с `TASK-001`.

### Сценарий B. Изменение существующей функциональности

1. Создать новую задачу с новым `taskId`.
2. В драфте ссылаться на существующие ID модулей, документов, полей и зависимостей.
3. Просматривать затронутые сущности и предполагаемый результат без их фактической замены.
4. Актуализировать карту только через публикацию драфта.

### Сценарий C. Параллельные задачи

1. Есть актуальная карта R3. Задачи A и B создают отдельные драфты от R3.
2. Публикация драфта A даёт R4. Драфт B остаётся неизменным и не публикуется автоматически.
3. При запросе публикации B система проверяет изменения между R3 и R4.
4. Если затронуты конфликтующие данные, остановить публикацию и показать конфликт. Нельзя молча переписывать R4.
5. После явного разрешения/пересборки драфта B позволить повторить предпросмотр и подтверждение.

### Сценарий D. Отказ от актуализации

1. Пользователь завершает задачу.
2. Приложение предлагает обновить карту.
3. Пользователь выбирает «Не сейчас»; текущая карта не меняется, драфт сохраняется для последующей работы.

## 5. Архитектурные сущности

Набор типов должен быть расширяемым, без предположений о реальном составе корпоративной системы. Начальные типы:

| Технический тип | Представляет |
|---|---|
| `system` | Систему или подсистему |
| `module` | Модуль |
| `feature` | Функциональность или сценарий |
| `zone` | Логическую группировку / функциональную область |
| `document` | Вид или экземпляр документа |
| `document_section` | Раздел документа, лист, таблицу или часть структуры |
| `file` | Конкретный файл или ссылку на него |
| `data_artifact` | Набор или результат обработки данных |
| `data_field` | Параметр / отдельное поле |
| `source_system` | Внешний или внутренний источник |
| `api` | API, контракт или иной интерфейс |
| `script` | Скрипт, обработчик, вычислительную операцию |
| `process` | Процесс |
| `requirement` | Требование |
| `decision` | Принятое или предлагаемое решение |

Базовые поля `Entity`:

```ts
type Entity = {
  id: string;               // постоянный ID, не зависит от координат или названия
  type: string;
  title: string;
  description?: string;
  architectureState: 'existing' | 'proposed' | 'unknown' | 'retired';
  confidence: 'confirmed' | 'unverified' | 'hypothesis';
  attributes?: Record<string, unknown>;
  evidenceIds?: string[];
  tags?: string[];
};
```

Неизвестные значения оставлять неизвестными. Предложение в опубликованном графе может оставаться со статусом `proposed`: опубликованность записи и факт реализации — разные характеристики.

### Документы, разделы и данные

Модель обязана отличать:

- логический документ от конкретного файла;
- формат файла (`PDF`, `XLSX`, `IFC`, `DOCX` и т. д.) от содержания документа; перечень форматов не закрытый;
- раздел/лист/таблицу документа от данных в нём;
- поле данных от набора данных и от способа получения;
- фактический источник данных от промежуточного преобразования и конечного потребителя.

Для документа: тип, назначение, допустимые форматы, версия, источник, владелец (если известен), ссылка на оригинал. Для раздела: родительский ID, путь/название внутри документа. Для данных: тип, единица измерения, периодичность, гранулярность, источник истины при наличии. Для скрипта/API: назначение, входы, выходы, условия, контракт и ссылка на реализацию при наличии.

## 6. Связи и происхождение данных

`Relation` содержит `id`, `sourceId`, `targetId`, `type`, `description?`, `attributes?`, `confidence?`, `evidenceIds?`.

Начальные типы отношений:

| Тип | Значение / пример |
|---|---|
| `contains` | Документ содержит раздел; раздел содержит поле |
| `part_of` | Функциональность входит в модуль |
| `produces` | Скрипт/процесс формирует артефакт |
| `consumes` | Модуль/функция использует данные |
| `reads_from` | Процесс получает данные из источника |
| `writes_to` | Процесс записывает результат |
| `transforms_to` | Данные преобразуются в другой артефакт |
| `provides` | API предоставляет данные |
| `calls` | Компонент вызывает API |
| `depends_on` | Объект зависит от другого объекта |
| `maps_to` | Поле источника сопоставлено полю назначения |
| `described_by` | Функциональность описана требованием |
| `justified_by` | Решение обосновано источником |
| `related_to` | Связь пока без уточнённой семантики |

Поддерживать направление, несколько различных связей между парой узлов, атрибуты связи и явную пометку гипотез. Не генерировать фиктивные связи для «красивой схемы». Для data lineage должен быть возможен путь **документ → раздел → поле → преобразование → артефакт → модуль**; неизвестные звенья обозначать как пробелы.

## 7. Графы и интерфейс — строго только чтение

### 7.1. Доступные представления

- **Актуальная карта** — опубликованные объекты и связи текущей ревизии.
- **Драфт задачи** — визуализация `CurrentMap@baseRevision + TaskDraft.operations`.
- **Сравнение** — актуальная карта и изменения драфта (`added`, `updated`, `archived`, затронутые связи).
- Позже — тематические срезы: «Документы», «Источники данных», «Один модуль», «API и обработчики».

Пользователь может переключаться между представлениями, но не редактировать их содержимое на графе.

### 7.2. Компоновка экрана

- **Слева:** список задач/драфтов, поиск и каталог сущностей, фильтры, переключение представления.
- **В центре:** read-only граф с узлами, связями, стрелками, подсветкой различий и функциональными «облаками».
- **Справа:** read-only карточка выбранной сущности или связи — поля, источник, связи, основания, статусы, история.
- **Сверху:** переключатель «Актуальная карта / Драфт задачи / Сравнение», базовая ревизия, автокомпоновка, действия просмотра.
- **При публикации:** отдельный экран/модальное окно с diff, конфликтами, подтверждением или отказом.

### 7.3. Разрешено на графе

- увеличивать, уменьшать и перемещать **камеру**;
- перетаскивать узлы для временной локальной настройки раскладки без записи координат в `CurrentMap`, `TaskDraft` или операции драфта;
- выбирать узлы и связи, открывать карточки;
- фильтровать, искать, скрывать/показывать группы и соседей;
- автоматически раскладывать граф и переключать сохранённые представления;
- показывать «облака» зон, пересечения функциональных областей и межзонные связи;
- визуально выделять `added`, `updated`, `archived`, `unknown`, `hypothesis` с текстовой легендой, не только цветом.

### 7.4. Запрещено на графе

- рисовать, создавать, удалять или соединять узлы и рёбра мышью;
- сохранять координаты узлов/зон как архитектурное изменение или операцию драфта;
- редактировать поля сущности или связи в инспекторе;
- применять драфтовые изменения кликом по узлу;
- изменять архитектуру кнопками «Добавить узел», «Добавить связь», «Изменить объект» на полотне.

Автораскладка, ручное перемещение узлов и другие параметры **просмотра** не являются предметными изменениями. Разрешён `drag nodes` только как локальное состояние раскладки; `connect edges`, переподключение рёбер, удаление и иной мутационный UI должны быть отключены.

## 8. Драфты: создание, согласование, публикация

### 8.1. Статусы

Предлагаемый цикл `TaskDraft`:

`draft` → `ready_for_review` → `published`  
`draft` / `ready_for_review` → `discarded`  
`ready_for_review` → `conflict` → (пересборка) → `ready_for_review`

`implementationStatus` задачи хранится отдельно (`unknown`, `design`, `in_progress`, `completed`) и не вызывает автоматического `published`.

### 8.2. Операции драфта

```ts
type ChangeOperation =
  | { op: 'createEntity'; entity: Entity; reason?: string; evidenceIds?: string[] }
  | { op: 'updateEntity'; entityId: string; patch: Partial<Entity>; reason?: string; evidenceIds?: string[] }
  | { op: 'archiveEntity'; entityId: string; reason?: string }
  | { op: 'createRelation'; relation: Relation; reason?: string; evidenceIds?: string[] }
  | { op: 'updateRelation'; relationId: string; patch: Partial<Relation>; reason?: string }
  | { op: 'archiveRelation'; relationId: string; reason?: string };
```

Существующие ID нельзя переопределять; системные поля ID, ревизий и происхождения не должны изменяться через произвольный `patch`. Перед реализацией сформировать строгие схемы валидации операций (например, Zod).

### 8.3. Запрос на актуализацию

Есть **два равноправных входа**:

1. **Пользователь сам инициирует:** команда/кнопка «Актуализировать карту по задаче».
2. **Система предлагает:** когда задача помечена завершённой, UI показывает «Задача завершена. Проверить изменения карты?» — варианты «Посмотреть», «Не сейчас».

В обоих случаях следующая стадия — **предпросмотр**, а не публикация. Отдельная кнопка «Опубликовать изменения» доступна только после валидации и показа diff. Нельзя публиковать в фоне либо при простом завершении задачи.

### 8.4. Публикация

1. Прочитать драфт и его `baseRevision`.
2. Проверить существование ссылок, ID, допустимые операции, типы полей и целостность связей.
3. Сравнить базовую ревизию с актуальной. При конфликтах заблокировать публикацию с подробным объяснением; предложить пересобрать драфт. Не делать автоматического слияния с потерей изменений.
4. Показать человеку **полный diff** и предупреждения о неподтверждённых сведениях.
5. Получить отдельное явное подтверждение.
6. Атомарно применить набор операций; создать новую ревизию и запись в истории с `taskId`.
7. Пометить драфт опубликованным; драфты других задач не изменять.
8. Если что-либо не прошло — не менять актуальную карту частично.

Архивация вместо физического удаления по умолчанию. Откат опубликованного изменения — отдельная новая контролируемая операция с историей.

## 9. Принцип работы в VS Code + Codex

В начальной версии пользователь работает преимущественно с текстовым описанием задачи, а Codex формирует предложенную модель изменений. **Не пытайся внедрить встроенный искусственный интеллект в приложение в первой версии.**

### Файловая структура данных (предложение)

```text
AGENTS.md
PROJECT_SPEC.md
README.md
data/
  current.json                  # опубликованная карта и номер ревизии
  tasks/
    TASK-001/
      task.md                   # описание задачи, требования, решения, ссылки
      draft.json                # предлагаемые операции по задаче
    TASK-002/
      task.md
      draft.json
  revisions/
    R0001.json                  # сохранённые опубликованные состояния / журнал
    R0002.json
```

Минимальный `current.json`:

```json
{
  "schemaVersion": 1,
  "projectId": "local-project",
  "revision": 0,
  "entities": [],
  "relations": [],
  "views": []
}
```

Минимальный `draft.json` (демонстрационная структура):

```json
{
  "schemaVersion": 1,
  "taskId": "TASK-001",
  "featureId": null,
  "baseRevision": 0,
  "status": "draft",
  "implementationStatus": "design",
  "operations": [],
  "evidence": [],
  "updatedAt": null,
  "publishedRevision": null
}
```

Метаинформация задачи находится в `task.md` и/или структурированных полях задачи. При реализации предусмотреть машиночитаемый ID/статус, не полагаясь на свободную интерпретацию Markdown.

**Принцип безопасности:** Codex при подготовке драфта меняет только файлы конкретной задачи и код приложения. Он **не редактирует `data/current.json` напрямую**. Обновление `current.json` допускается исключительно сервисом публикации после подтверждения в приложении. Для первоначального bootstrap пустой карты использовать отдельную команду и не смешивать её с повседневной актуализацией.

Текущую карту и историю сохранять безопасно (временный файл, проверка, атомарная замена либо эквивалентная надёжная транзакция). При изменении формата выполнять миграцию. История должна переживать перезапуск приложения.

## 10. Техническое предложение

Это **предложение стека для нового приложения**, не сведения о существующей корпоративной платформе:

- Frontend: React + TypeScript + Vite.
- Graph display: `@xyflow/react` в **read-only режиме**; позже автоматическая раскладка ELK.js/Dagre по результату технического выбора.
- Локальный API: Node.js + Fastify (либо сопоставимое лёгкое решение).
- Проверка схем: Zod.
- Тесты: Vitest; ключевые сценарии UI — Playwright по возможности.
- Файловое хранение JSON для первого MVP с отдельным слоем репозитория, допускающим последующий переход на SQLite.

Не нужна авторизация, платформа совместного редактирования, сервер в облаке или внешняя LLM в MVP. UI не пишет в локальные файлы в обход API. Прикреплённые пути к документам — метаданные, а не разрешение читать произвольные локальные файлы. Архитектурные сущности `script` не исполнять.

### Логические компоненты

1. `ArchitectureRepository` — чтение опубликованной карты и истории.
2. `TaskRepository` — задачи и их независимые драфты.
3. `DraftValidator` — проверка операций, ссылок и ревизий.
4. `DraftProjector` — вычисление графа драфта из базы и операций без записи в `CurrentMap`.
5. `DiffService` — добавленные/изменённые/архивированные объекты и связи.
6. `PublishService` — единственная операция записи опубликованной карты.
7. `GraphPresenter` — read-only отображение, раскладка, зоны, выбор, поиск, фильтрация.

Реализовывать по мере этапов, не создавать директории-заглушки без работающих компонентов.

## 11. Приоритеты реализации

### P0 / основная версия

- Read-only актуальная карта с масштабированием, панорамированием, поиском, выбором и просмотром свойств.
- Канонический реестр сущностей и типизированных связей; без создания элементов мышью.
- Локальное хранение актуальной карты и отдельных драфтов по `taskId`.
- Создание задачи и добавление/обновление текстового описания.
- Импорт/чтение `draft.json`, подготовленного Codex; валидация.
- Отдельное графическое представление драфта каждой задачи.
- Diff драфта относительно базовой ревизии и текущей карты.
- Предложение актуализировать карту после завершения задачи и возможность вручную инициировать процедуру.
- Явное подтверждение, атомарная публикация и новая ревизия истории.
- Проверка конфликтов при публикации драфтов от устаревших ревизий.
- Импорт/экспорт данных проекта, понятные ошибки, перезапуск без потери данных.

### P1 / развитие

- Несколько тематических read-only срезов одной модели.
- Сворачиваемые зоны-«облака», разделы документов, автоматическая раскладка больших графов.
- Глубокая детализация документов, форматов, разделов, параметров.
- Data lineage и impact analysis по типам связей и глубине.
- История отдельных объектов с переходом к задачам, изменившим их.
- Поиск пропусков в источниках и несогласованности описаний, без выдачи гипотез за факты.

### P2 / не делать без нового задания

- Встроенный AI-чат для автоматического создания/обновления драфта.
- Извлечение структуры из PDF/DOCX/XLSX/IFC и других файлов.
- Интеграции с Jira/Confluence/CDE/Git и корпоративными API.
- Многопользовательская совместная работа, роли, внешние согласования.
- Выполнение описанных архитектурных скриптов.
- Формальная поддержка редакторов ArchiMate/UML/DFD.

## 12. Этапы для Codex

**Этап 1 — Каркас и просмотр.** React-приложение, read-only диаграмма, каталог, инспектор, пустая актуальная карта, модель `Task`/`TaskDraft`, локальный API и сохранение, README. Никакого редактора графа.

**Этап 2 — Драфты задач.** Каталог задач, чтение/сохранение описания, импорт и проверка `draft.json`, построение `DraftPreview`, переключение актуальной карты и драфтов. Изоляция по задачам.

**Этап 3 — Актуализация.** Diff, ручной вызов и предложение после завершения задачи, обязательное подтверждение публикации, проверка конфликтов, атомарное изменение карты, история ревизий.

**Этап 4 — Детализация.** Документы и разделы, артефакты данных, источники, скрипты, API, семантические связи, просмотры происхождения данных.

**Этап 5 — Улучшение визуализации.** Зоны, автокомпоновка, большие графы, тематические срезы, фильтры, навигация по истории и зависимостям.

## 13. Приёмочные сценарии

### A. Запрет ручного редактирования

1. Открыть актуальную карту и драфт.
2. Перетащить узел; затем попытаться создать связь drag-and-drop, удалить узел и изменить значение карточки.
3. Убедиться, что узел меняет только локальную позицию, остальные действия недоступны, а содержимое файлов архитектуры не меняется.
4. Проверить, что масштабирование, панорамирование и выбор работают.

### B. Отдельный драфт каждой задачи

1. Создать `TASK-A` и `TASK-B` на ревизии R1.
2. В драфт A добавить документ и поле; в драфт B — другой модуль и связь.
3. Открыть карту R1: ни одно предложение не видно как опубликованное.
4. Открыть драфт A: видны только изменения A. Драфт B: только изменения B.
5. Перезапустить приложение: текущая карта и оба драфта сохранились.

### C. Запрос на актуализацию

1. Завершить задачу A: показать предложение актуализировать карту.
2. Нажать «Не сейчас»: ничего не публикуется.
3. Затем вручную вызвать актуализацию и увидеть diff.
4. Нажать «Опубликовать» после подтверждения: получить R2, связанный с задачей A.
5. Проверить, что B не опубликован автоматически и история R1 сохранена.

### D. Конфликты

1. Создать драфты A и B на одной ревизии R1, где оба предлагают разные изменения одного поля.
2. Опубликовать A как R2.
3. Попытаться опубликовать B: получить ошибку конфликта и перечень затронутых элементов.
4. Подтвердить, что R2 не перезаписана данными B.

### E. Документ → поле → артефакт → модуль

В отдельном демонстрационном наборе представить документ «График» (`XLSX`), раздел, поле «Плановая дата», артефакт «Плановые сроки» и модуль «Мониторинг». Показать цепочку отношений и происхождение данных без дублирования объектов и без возможности отредактировать граф мышью. Демо не является описанием реальной системы.

## 14. Что нужно решить позже (не блокирует Этап 1)

- Один драфт строго на задачу или допускается несколько альтернативных драфтов внутри задачи? Сейчас: **один активный**.
- Как именно определять «задача завершена» — вручную, из репозитория кода или из таск-трекера? Сейчас: **ручная отметка**.
- Где будет запускаться интеллектуальное формирование драфта — только Codex в VS Code или встроенный помощник? Сейчас: **Codex в VS Code**.
- Какое поведение при публикации не пересекающихся изменений от разных базовых ревизий? Сейчас: **консервативная проверка, без молчаливого слияния**.
- Нужна ли отдельная модель «тип документа» и «экземпляр документа»? Отложить до кейсов с реальными данными.
