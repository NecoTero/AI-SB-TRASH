# Черновик концепции правил классификации работ

Дата фиксации: 6 ноября 2026 года  
Статус: временная рабочая заметка для продолжения обсуждения

## Исходная идея

Текущий инструмент признаков формирования работ решает задачу распознавания исходных данных:

1. Находит в IFC системный атрибут по одному из настроенных ключей.
2. Приводит разные исходные написания к единому мастер-значению.

Примеры распознаваемых атрибутов: Код КФО, Корпус и Этаж.

Строительный этап относится к другому уровню. Он не обязательно хранится в IFC как готовый параметр, а вычисляется из уже распознанных системных атрибутов. Сейчас этап определяется только по КФО. Требуется развить эту механику так, чтобы результат мог зависеть от нескольких атрибутов, например от КФО и этажа одновременно.

## Предлагаемое разделение инструментов

Не следует смешивать распознавание исходных значений и вычисление бизнес-классификации в одной сущности.

### Признаки формирования работ

Отвечают на вопрос: как найти и нормализовать КФО, корпус и этаж?

- ключи параметров IFC;
- приоритет ключей;
- мастер-значения;
- допустимые варианты исходных значений.

### Правила классификации работ

Отвечают на вопрос: какой бизнес-результат получить из комбинации уже распознанных атрибутов?

- входные системные атрибуты: КФО, Корпус, Этаж и другие;
- условия над их мастер-значениями;
- результирующее значение классификатора;
- проверка конфликтов и непокрытых данных.

Общая цепочка:

```text
Исходные параметры IFC
        ↓
Распознанные системные атрибуты
КФО · Корпус · Этаж
        ↓
Правила классификации
        ↓
Строительный этап · Зона · Пакет работ · другие результаты
```

## Рекомендуемые названия

- Раздел системы: **Классификация работ**.
- Экран: **Правила классификации**.
- Настраиваемая сущность: **Классификатор**.
- Первая сущность: **Классификатор «Строительный этап»**.

Текущий инструмент можно оставить под названием **Признаки формирования работ** либо уточнить как **Атрибуты формирования работ**.

Не рекомендуется называть новый инструмент просто «Признаки работы»: это затруднит различение найденного в IFC атрибута и вычисленного результата.

## Модель правила

Пример определения этапа «Фундамент»:

```text
Результат: Фундамент

Когда:
Код КФО — одно из [204.02.01.01, 204.02.01.02]
И
Этаж — одно из [Этаж -2, Этаж -1, Этаж 0]
```

Пример определения этапа `Shell&Core` для тех же КФО на других этажах:

```text
Результат: Shell&Core

Когда:
Код КФО — одно из [204.02.01.01, 204.02.01.02]
И
Этаж — одно из [Этаж 1 … Этаж 20]
```

Так один и тот же КФО может приводить к разным этапам в зависимости от этажа.

## Логика объединения условий

Для первой версии предлагается ограниченная и понятная логика:

- несколько значений внутри одного условия соединяются через **ИЛИ**;
- разные атрибуты внутри одного правила соединяются через **И**;
- для одного результата можно создать несколько групп правил, соединённых через **ИЛИ**.

Пример:

```text
Фундамент =
  (КФО входит в список A И Этаж входит в список B)
  ИЛИ
  (КФО входит в список C И Корпус = Корпус А)
```

В первой версии не нужны произвольные скобки, вложенные выражения, оператор `НЕ` и сложный язык формул. Они заметно усложнят интерфейс, диагностику и проверку правил.

## Предлагаемый интерфейс

Можно использовать композицию уже существующего конструктора маршрута: структура слева, настройка выбранного элемента справа.

### Верхняя часть формы

- наименование классификатора;
- описание;
- статус: черновик или активен.

### Левая колонка

Список возможных результирующих значений:

```text
Фундамент
Shell&Core
Фасады
Кровля
FitOut
+ Добавить значение
```

### Правая колонка

Редактор правил выбранного значения:

```text
Фундамент

Группа правил 1
Код КФО     [одно из]  [55 значений]
Этаж        [одно из]  [-2, -1, 0]

+ Добавить условие
+ Добавить альтернативную группу
```

Значения строительного этапа не являются последовательными шагами, поэтому в интерфейсе лучше называть их результатами или значениями классификатора, а не этапами маршрута.

## Проверка перед сохранением

До применения правил система должна показывать:

- количество работ или IFC-элементов для каждого результата;
- количество объектов без результата;
- объекты, одновременно попавшие в разные результаты;
- правила, которые не нашли ни одного объекта;
- объекты без необходимого входного атрибута, например без этажа.

Для первой версии рекомендуется блокировать сохранение пересекающихся правил. Скрытый выбор первого подходящего правила опасен: администратор может не заметить, что один объект соответствует двум этапам.

Если в дальнейшем пересечения окажутся необходимы, можно добавить явный приоритет правил.

## Миграция текущего строительного этапа

Текущий справочник `КФО → строительный этап` можно автоматически преобразовать без изменения поведения:

```text
Фундамент → Код КФО входит в текущий список фундаментных КФО
Shell&Core → Код КФО входит в текущий список Shell&Core
Фасады → Код КФО входит в текущий список фасадных КФО
Кровля → Код КФО входит в текущий список кровельных КФО
FitOut → Код КФО входит в текущий список FitOut
```

Каждое текущее соответствие станет правилом с одним условием. После миграции пользователь сможет добавить к нему условие по этажу, корпусу или другому распознанному атрибуту.

## Важные ограничения

- Строительный этап остаётся классификационным атрибутом и не входит в идентификатор работы `КФО + Корпус + Этаж`.
- Правила должны работать с нормализованными мастер-значениями, а не с сырыми строками IFC.
- Одинаковая логика в перспективе должна применяться к IFC и графику, если оба источника содержат необходимые распознанные атрибуты.
- При изменении активных правил потребуется определить единый сценарий пересчёта уже загруженных данных: автоматический пересчёт либо явная команда с пометкой о неактуальности результата.

## Итоговая рекомендация

Сохранить текущий инструмент распознавания без принципиального усложнения и добавить над ним отдельный конструктор правил классификации.

«Строительный этап» станет первым классификатором, но не специальной жёстко зашитой сущностью. В дальнейшем по той же модели можно создавать зону производства работ, очередь строительства, пакет работ, тип конструкции и другие вычисляемые атрибуты.

## Следующий шаг обсуждения

Перед реализацией следует подготовить один экран конструктора и проверить его минимум на трёх сценариях:

1. Этап определяется только по КФО.
2. Один КФО разделяется на разные этапы по этажу.
3. Два правила пересекаются, и система показывает понятный конфликт.
